# Development

This repository is nanocode-ts (gakonst/nanocode-ts, formerly nanocode-wasm): the nanocode Rust SDK compiled into one WebAssembly module, the TypeScript host that runs it in any JavaScript runtime that can instantiate WebAssembly, such as Cloudflare Workers, Node, Deno and browsers, and TypeScript adapters for Vercel and Cloudflare, so a host repository writes only TypeScript and builds no Rust. Its sibling `../nanocodex` supplies the SDK; `sdk-revision.json` records the SDK master revision this package builds against; check out that revision in the sibling when preparing a fresh workspace. `.github/workflows/release.yml` builds every push to main against the SDK at `sdk-revision.json`, checked out beside it as `nanocodex/`, with the Rust release `rust-toolchain.toml` pins, checks it, packs it and publishes the tarball as the GitHub release `build-<short commit>`. Hosts install that tarball, `"nanocode-ts": "https://github.com/gakonst/nanocode-ts/releases/download/build-<short commit>/nanocode-ts-<short commit>.tgz"`, which their lockfile pins with its integrity: gakonst/nanocode-cloudflare-durable (formerly nanocode-worker) and gakonst/nanocode-vercel-durable; tempoxyz/nanocode-site builds the package from a checkout instead. `dist/` is build output, ignored by Git and listed in `package.json`'s `files`, so the tarball carries the compiled JavaScript, declarations and module and installing it needs neither Rust nor a TypeScript build. Commits before the releases kept `dist/` in Git, so their `github:gakonst/nanocode-ts#<commit>` pins still install. Generic agent, durability, turn and event logic belongs in the SDK, host-agnostic bridge glue in `src/*.ts`, a platform's generic plumbing in its adapter under `src/<platform>/`, and an application's business logic (routes, tools, authorization, UI) in the host repository.

Do not add code comments, README files, Cargo features, wasm-bindgen glue, tests, or test-only dependencies. The host-agnostic sources use no platform types or bindings: no `DurableObjectState`, no `@cloudflare/workers-types`, no Node APIs; `tsconfig.json` checks `src/*.ts` and `src/cloudflare/*.ts` against the standard web platform types only, and `tsconfig.vercel.json` checks `src/vercel/*.ts` against Node's. Hosts supply everything platform-specific through the interfaces below or take an adapter's. The Rust side is single-threaded and keeps its state in `thread_local` cells, with no `Mutex` or `RwLock`. TypeScript uses only erasable syntax (`erasableSyntaxOnly`, `verbatimModuleSyntax`) and imports with `.ts` extensions, so Node 22.18 or newer runs the sources directly with type stripping from a checkout or a `file:` link, and bundlers such as esbuild and Wrangler compile them. Limits come from host policy passed in, not from constants here.

`package.json` exports the compiled host as `nanocode-ts`, the adapters as `nanocode-ts/vercel` and `nanocode-ts/cloudflare`, the browser client as `nanocode-ts/client`, the model catalog as `nanocode-ts/models`, the simulated shell as `nanocode-ts/bash`, and the compiled module as `nanocode-ts/nanocode_wasm.wasm`, with declarations beside each file. `nanocode-ts/models` is generated by `scripts/build.mjs`, which instantiates the module it built and writes `AgentRuntime.modelCatalog()`: each harness's models with their display name, the reasoning efforts the SDK's `ModelCapabilities` allow and its default, whether it takes the priority service tier, and the gateways that serve it (`direct`, `vercel`, `workers_ai`), so hosts render pickers and validate requests from the SDK instead of copying its tables; a Claude-harness model outside the catalog, such as `zai/glm-5.3`, stays host policy. `nanocode-ts/client` imports nothing, so a page can load `dist/client.js` as a static module: `liveEvent` maps logged events to the vocabulary the Vercel adapter streams (`text`, `reasoning`, `tool_input`, `tool_start`, `tool_end`, `turn`, `retrying`), `Transcript` reveals text and reasoning at 1 − e^(−t/`revealMs`) per frame (instantly with `revealMs: 0` or reduced motion), posts finished paragraphs (`paragraphs`, which keeps code fences whole) as entries, turns tool, retry, error, steer and failed-turn events into entries (`describe`), shows a `tool_input` stream as a live `tool` entry, the tool's name and its input as `ToolInput` decodes it, until the call's next event replaces it with the call's own entry and hands every other event to the host's `apply` in order, `serverEvents` reads a Server-Sent Events body, and `modelItems` and `thinkingItems` build the composer's pickers. `ToolInput` decodes a tool call's input as `tool_input` deltas arrive, in one pass over each delta: `fields` holds each top-level string field of a JSON object, unescaped and growing as the model writes it, and `text()` the only field, `key: value` lines for several, or the raw text of a freeform input such as Codex's `exec` source, so a page can show a file's content or a page's markup while the model writes the call; 600 random chunkings of three inputs (escapes, \u sequences, emoji, a 5 KB field, nested objects and arrays) decoded to the fields `JSON.parse` reads. The three chats, gakonst/nanocode-vercel-durable's, gakonst/nanocode-cloudflare-durable's and nanocode.xyz's, share it. A bundler that loads `.wasm` imports as `WebAssembly.Module`, as Wrangler does, imports it directly; other hosts compile `dist/nanocode_wasm.wasm` with `WebAssembly.compile`, as the Vercel adapter does.

`nanocode-ts/vercel` runs a session as a durable-harness kernel `Harness` (`nanocodeHarness`, for `durableAgent({ harness })` from `durable-harness`, an optional peer dependency): every SQL write of the SDK's store and turn log is a record-only kernel step `nanocode.sql` keyed `sql:<n>` in the session's Workflow run, each drive replays the committed batches into a `node:sqlite` `:memory:` database (`SqlJournal`, `LocalSql`), submissions become turns of the SDK's `TurnInbox`, host tools are durable-harness `HostTool`s run as kernel steps `tool:<call_id>`, logged events reach the live stream in durable-harness's vocabulary, and model requests go to the Vercel AI Gateway with `AI_GATEWAY_API_KEY` or the Vercel OIDC token (`@vercel/oidc`, an optional peer dependency). A session's provider, model and reasoning effort come from the `nanocode: { provider, model, thinking, max_tokens }` entry of its kernel config when the host starts it with one (`agent.sessions.start({ config })`), as gakonst/nanocode-vercel-durable does for the harness and model a visitor picks, and otherwise from the harness options; the `nanocode.session` effect records them, so every drive opens the same backend and model, and the model endpoint follows the session's provider. A prompt whose whole text is `/effort <level>` is a command, not a turn: the drive checks the level against the session's model with `checkThinking`, records it or the SDK's refusal as that submission's placement, and sends the live stream `{"type":"effort","thinking"}` or an `error`. A submission of kind `steer` that arrives while a turn runs steers it: the drive watches for submissions while `drive` runs (durable-harness's `onHint`, or every `WAIT_POLL_MS` without hints), steers each with its submission ID, records the placement and sends the live stream `{"type":"steered"}`, and `text` and `reasoning` deltas carry the `item` they belong to, the output item or `reasoning:<model call>`, so a reply that follows a steer starts a new message; one that no running turn takes is submitted as a turn when the drive returns. `streamToolInput: true` passes `stream_tool_input`, so the live stream also carries `tool_input` events while the model writes a tool call. `maxPrompts` caps the prompts a session takes, counting every submission but `chaos` and `withdraw` in log order: the drive records a submission past it as placed with `nanocode.refused` and sends the live stream an `error`, and does not steer with it, so a public host enforces its cap inside the drive instead of reading the session before each submission, which cost gakonst/nanocode-vercel-durable 82–108 ms per prompt on 2026-10-21. Every later prompt is submitted with the effort in force as `metadata.thinking`, derived from the placements before it in the run's log so each drive derives the same one, and the drive calls `setThinking` before it drives a turn whose effort differs from the last it applied. `durability: "on"` acknowledges writes at once under the kernel's run-ahead durability and `"strict"` only after their batch commits. `openReader` answers the SDK's reader commands from a session's fold. It reads the module from `dist/nanocode_wasm.wasm` beside itself (`new URL("../nanocode_wasm.wasm", import.meta.url)`). gakonst/nanocode-vercel-durable records its design, limits and measurements.

`nanocode-ts/cloudflare` is the Durable Object side: `DurableObjectSql` is the `SqlHost` over a Durable Object's `storage.sql.exec` and `transactionSync`, with workerd's 8 MiB value limit (`SQLITE_VALUE_LIMIT_BYTES`, where its SQLite answers SQLITE_TOOBIG) as `value_limit`, and an optional observer of each transaction's statements, rows read and written and duration. Its storage type is structural, so the adapter needs no `@cloudflare/workers-types`. gakonst/nanocode-cloudflare-durable builds its session Durable Object on it.

`AgentRuntime.instantiate(module, sql, { published, wake })` instantiates the module for one session scope; `submit`, `turn`, `pending`, `page`, `cancel`, `interrupted`, `retry`, `finish`, `import`, `catalog` and `admit` run on that instance through the SDK's `SessionLog` without opening the SDK session, and `open(config, options)` opens it on the same instance; it cannot be opened twice. `config.model` names a model of `config.provider`, such as `gpt-6-luna` or `claude-haiku-5-5`, and `config.thinking` its reasoning effort; without them a session uses Sol or Opus 5.5 at the model's default effort. A Codex session's model must be a Codex model; a Claude session takes any model ID since SDK f96a9a0d7, a Claude model ID or alias or another model a Messages gateway serves, such as `zai/glm-5.3` or `moonshotai/kimi-k3` on the Vercel AI Gateway, and a model the SDK does not know needs `config.max_tokens`, its output limit, which the Rust side applies through `ClaudeHarness::configure`. `config.gateway: "vercel"` routes a Codex API-key session through the SDK's `ResponsesGateway::vercel()`, which names OpenAI models with the gateway's `openai/` prefix and also serves the open-weight GLM-5.3, Kimi K3 and MiMo V2.6 Pro (`config.model` `glm-5.3`, `kimi-k3` or `mimo-v2.6-pro`) as `zai/glm-5.3`, `moonshotai/kimi-k3` and `xiaomi/mimo-v2.6-pro` since SDK 3d983dea2, at `config.endpoint` (`https://ai-gateway.vercel.sh/v1`); a ChatGPT subscription with it is a configuration error, and Claude sessions need only the gateway's Messages URL as `config.endpoint`, since the Vercel AI Gateway accepts Claude's own model IDs. `config.gateway: "workers_ai"` with `config.cloudflare_account_id` runs a Codex API-key session on Workers AI through the SDK's `ChatGateway::workers_ai`, which serves GLM-5.3 (`glm-5.3`) as `@cf/zai-org/glm-5.3` and translates its Responses requests to Chat Completions inside the module: `dispatch` receives them with an `endpoint` ending in `/chat/completions` at that account's `/ai/v1`, and `config.endpoint` is not used. `config.service_tier` (`standard`, `priority` or `fast`) is a new session's initial service tier, which the SDK sends to OpenAI models as `service_tier: "priority"` and refuses as a configuration error for models without a faster tier, such as Claude models other than Opus 5.5. `config.stream_tool_input: true` logs and publishes the SDK's `tool.input.delta` events, each tool call's input as the model writes it with its `call_id` and `tool`, which `liveEvent` maps to `tool_input` events with `name`, `delta` and `call_id`, so a page can show code, a file or a frame while the model writes the call; it turns on the SDK's `tool_input_deltas` on both backends, and without it the agent emits none, because the log would store every tool input twice. `config.subagents: false` leaves out the delegation tools, and the `hands` tool is offered only to sessions with a remote executor or hands. On 2026-10-21 through the Vercel AI Gateway, nanocode-vercel-durable's first Luna request with its six workspace tools held 796 input tokens instead of 2,469 (6 KB instead of 17.6 KB, and 2.6 KB instead of 15.5 KB for Claude), and the priority tier moved Luna's median time to first text from 989 to 792 ms over 8 requests each, the slowest from 1,750 to 995 ms. The host passes the configuration through unchanged except for the fields it adds (`runtime_id`, `started_ms` and the defaults of `provider`, `remote`, `hands`, `event_coalesce_ms` and `tools`), and the Rust `Configuration` denies unknown fields, so a misspelled or unsupported field is a `configuration` refusal at `open` instead of a silently ignored one; `scripts/build.mjs` fails when `AgentConfiguration` and the Rust `Configuration` name different fields. Before, `open` copied a fixed list of fields and dropped `max_tokens` until it was added there. `config.instructions` adds host instructions to the agent's developer context, before the hand placement instructions when Code Mode has an executor or hands. `identity` reads the name and runtime ID a hand's catalog advertises, and `catalog` only the name. `retry` records why a turn waits on its host, with an error, kind and next retry time, and `finish` ends a turn the host gives up on as failed or cancelled. `open` throws `HostFailure` with kind `configuration` and `permanent` set when the SDK refuses the runtime configuration or the session it opens, such as a reasoning effort its model does not take, so a host can fail the turn instead of retrying it (before, the session's refusal was a plain error and durable-harness redelivered the drive without end); hosts construct `HostFailure` for their own classifications too. `drive` runs the SDK's `TurnInbox` for one root turn, `settle` reports quiescence, `attach` and `detach` register hands, `preconnect` opens a Codex socket early, `steer(requestId, prompt)` steers the running turn through the SDK's `TurnInbox::steer` with an identified steer and answers false when no turn takes it, `checkThinking` checks a reasoning effort against the session's model and `setThinking` also applies it to the model calls that follow, which both backends allow at any time (`Mutability::Anytime`), `connected` reports whether it holds an open model socket, `releaseConnections` closes model sockets and `dispose` shuts the SDK session down. A model response body or Codex socket that the SDK cancels after the host registered it, before the reply reached WASM, is cancelled or closed at once instead of staying open until `dispose`. `metrics` reports counters, WASM memory, timing spans and the last `RECENT_MODEL_LIMIT` (64) model dispatches, the retention policy for diagnostics. `sessionUuid()` makes the UUIDv7 session IDs the SDK requires, and the host uses it for its runtime ID too, because `crypto.randomUUID` is missing from some iOS browsers, such as Brave, where `crypto.getRandomValues` works.

Hosts implement these interfaces (`src/contracts.ts`):

- `SqlHost.transaction(kind, operation, statements)` runs one operation's statements in one atomic SQLite transaction and returns each statement's rows as arrays. `SqlHost.value_limit`, when set, is the largest string, BLOB or row the host's SQLite stores: `instantiate` passes it to the module with the `configure` command before any other, and the module gives it to every scope's `SessionLog` as `value_limit`, so an event above it is logged as an `omitted` marker, a result above it fails its turn, `submit` answers `{"submitted":"too_large","bytes","limit"}` for a prompt whose turn or input.accepted event would not fit, and `import` batches within it. `kind` is `store` for the SDK's `SqlStore` and `log` for its `SessionLog`; the SDK owns the `states`, `owners`, `blobs`, `records`, `turns` and `events` tables and every statement (since SDK 197a41a8c records go to `blobs` and `records` holds only what earlier builds wrote), binds only text parameters and reads text or null. Durable Objects' `transactionSync`, `node:sqlite` and sqlite-wasm satisfy it synchronously; an asynchronous host may return a promise.
- `published(events, bytes)` receives each batch the SDK's `SessionEvents` pump logs, already committed, in sequence order, with each event's encoded JSON size in bytes; `wake()` runs after the SDK's remote Code Mode client receives a batch or finishes a callback, so a host can check quiescence again.
- `dispatch(request, signal, timing)` sends a model HTTPS request and returns a fetch `Response`. The body crosses from WASM as raw bytes and must be forwarded unchanged. The host owns credentials: Claude clients send no authentication headers and Codex uses `OpenAiAuth::host_managed_chatgpt()` for subscriptions and `OpenAiAuth::gateway_managed()` for API keys, so the host or its egress injects them. Redirects are refused.
- `socket.open(request, signal, timing)` opens a Codex Responses WebSocket with the SDK's handshake headers and returns a `SocketHandshake`: the status, response headers, an open `MessageSocket` (`send`, `close`, `addEventListener` for `message`, `close` and `error`) on 101, an optional `idle_ms` read deadline and `text()` for a rejected handshake's body. `socket.admit()` runs before every frame is sent, so a host can wait for durability or refuse a cancelled turn's frames.
- `tools.call(name, input, signal, context)` runs a host tool; `context.call_id` is the SDK's `ToolContext` call ID, the model's tool call ID or `<call>/code-<n>` for a Code Mode nested call, which stays the same when a turn replays, so a host can key its own record of the call or an idempotency key on it. Each `config.tools` definition's `name`, `description` and JSON Schema `parameters` become the SDK's `FunctionTool` with parallel calls, offered directly and inside Code Mode on both backends; a string result becomes the tool's text output and any other result its JSON output, a thrown error a tool error, and a definition with `content: true` may also answer `{ content, structured_result? }`, whose `input_text` and `input_image` items (a data URL and a `detail`) become a text-and-image output through the SDK's `FunctionTool::content_results`, so a tool can show the model a screenshot or preview without a Rust tool, and the SDK keeps the call's receipt like any tool's.
- `remote.execute(request, id)`, `cancel(id)` and `dispose()` carry the SDK's remote Code Mode frames for a configured executor (`connection` null) and for hands. `RemoteExecutor` implements them over any `MessageSocket`: `connect(open, policy)` dials and listens within `timeout_ms`, `accept(socket, policy)` and `restore(socket, policy, catalog)` take a socket whose messages the host forwards to `receive` and `disconnected`, as a hibernating Durable Object does. It keeps frames opaque, enforces `max_frame_bytes`, keeps the first frame as the catalog and lets one runtime own a hand connection at a time (`claim`, `owns`, `release`). `refuse(reason)` closes a connection with 1008 and the reason in the close frame, so the hand can read it. A host that sends none of a `remote_send` batch throws `RemoteRefusal`, which crosses the bridge marked unsent: `RemoteExecutor` throws it when its connection already failed or its first frame cannot be sent, and hosts throw it for their own refusals, such as a revoked hand or a cancelled turn, before any frame reaches the socket. The SDK then reports the batch's operations as not dispatched instead of as unknown outcomes; any other error leaves them unknown.

`LocalHand` (`src/hand.ts`) is a hand that runs in the host's own JavaScript runtime: `config.code_mode: true` turns Code Mode on for a session without a machine, and `open` uses the `LocalHand` passed as `options.remote` or a default one. It implements the `remote` contract directly and speaks the SDK's remote Code Mode frames unchanged, so the brain side is the same `RemoteClient` that serves hands: its catalog publishes no tools of its own, every Execute's `local_tools` (the session's host tools and the SDK's delegation tools) become `tools.<normalized name>` inside the cell, whose calls go back to the brain as `Callback` frames with the call ID `<exec call>/code-<n>`, and `exec` and `wait` are the only tools the model calls directly, as on native builds. A cell is an `AsyncFunction` in the host's realm whose parameters shadow the native Code Mode globals (`tools`, `ALL_TOOLS`, `toolSchema`, `text`, `image`, `audio`, `generatedImage`, `notify`, `store`, `load`, `yield_control`, `exit`, `setTimeout`, `clearTimeout`) plus `fetch`, the host's `options.fetch` (`globalThis.fetch` by default) bound to the cell's abort signal, and `bash` when the host passes `options.bash` (see `nanocode-ts/bash` below); a host passes a paying fetch, such as mppx's `Mppx.create(...).fetch`, so every request a script makes is paid without a payment tool. It follows `crates/runtime/code-mode`'s cell semantics: the `// @exec:` pragma, the 10 s initial and wait yields with the 1 s observer grace from 10 s up, `Script running with cell ID <n>`, `Script completed`, `Script failed` with `Script error:`, `Script terminated`, the `Wall time` header, `max_output_tokens` and `max_tokens` truncation, session-scoped cell IDs and `store` values, and `wait` with `terminate`. A terminated or cancelled cell (`CancelTurn`, `Cancel`, `dispose`) aborts its fetches, clears its timers, cancels its pending callbacks and drops its later output; the script itself runs to its next await, because a realm cannot stop a running function. `wasm.rs` installs the remote host as the default executor `local` (`config.executor` renames it) without the `hands` tool or `PLACEMENT_INSTRUCTIONS`, which describe machines, and adds `LOCAL_INSTRUCTIONS`, which tells the model that `fetch` works, since the upstream `exec` description says scripts have no network access; `code_mode` with `remote` is a configuration error. Browsers, Node, Deno and Bun run the in-realm evaluator, and a page whose Content Security Policy omits `'unsafe-eval'` cannot. Cells run through a `CellEvaluator`: the default, `inRealm`, builds the cell's scope from `CELL_SCOPE` (`src/cell.ts`, the globals as JavaScript source, so one definition serves every evaluator) and runs the script as an `AsyncFunction` in the host's realm. Cloudflare Workers refuse code generation from strings, so `nanocode-ts/cloudflare` exports `workerLoader(env.LOADER)`, an evaluator that runs each cell as its own Dynamic Worker (a `worker_loaders` binding) with `globalOutbound: null`: the cell's module embeds `CELL_SCOPE` and the script, and reaches the host only through the RPC stubs of a plain object, whose `fetch` takes a `Request` that the hand replays through the host's fetch with a buffered body, so a paying fetch can retry it after a 402; the scope waits for its pending RPC calls before it returns, because a `text()` call still in flight when `run` returned arrived after the cell had settled and was dropped. On 2026-10-22 a Durable Object under `wrangler dev` (workerd) ran the scripted Codex mock with `workerLoader` cells, a host tool, a paid POST, `notify`, `store`, a yield resumed by `wait`, a thrown error and a syntax error, about 25 ms per cell; a probe Worker in the Tempo Development Resources account ran a Loader cell with a host tool and fetch in 22-28 ms. `nanocodeHarness({ codeMode: true, fetch })` opens the Vercel adapter's sessions in Code Mode with an in-realm `LocalHand`; a cell does not outlive its drive. On 2026-10-22 `output/code-mode.mjs` (a scripted Codex mock in Node) ran a cell that called a host tool and the injected fetch and used `text`, `notify`, `store` and `image`, a 100 ms yield resumed by `wait`, a missing tool, a thrown error and a `yield_control` cell ended by `terminate`; every request offered only `exec` and `wait` directly, with the host tool `direct: false` and its `code_mode_name` set.

`nanocode-ts/bash` (`src/bash/`) is a simulated bash for agents, written here from scratch in the spirit of vercel-labs/just-bash and not depending on it: a parser and interpreter over a virtual filesystem with no processes, so it runs wherever the host does, Workers included, since it generates no code from strings. `await Bash.create({ files, fs, env, cwd, fetch, limits, commands })` makes a shell whose `exec(script, { stdin, env, cwd, signal })` answers `{ stdout, stderr, exitCode, truncated }`; every `exec` starts from fresh variables, functions and working directory (`/home/user` by default) while the filesystem persists, and `readFile`, `writeFile` and `fs` reach it from host code. `fs` is a `FileSystem` (async `stat`, `read`, `write` with append, `list`, `mkdir`, `remove`, `rename` over absolute paths), `MemoryFileSystem` by default, so a host can back it with the Tempo gateway's bucket or kv. `src/bash/syntax.ts` parses words, quoting, `$'...'`, parameters with `${...}` operators, `$(...)` and backticks, `$((...))`, pipes, `&& || ; &`, redirections (`> >> < 2> 2>&1 &> <<<` and `<<` or `<<-` heredocs), `if`, `for` in both forms, `while`, `until`, `case`, groups, subshells, `(( ))`, `[[ ]]` and functions; `src/bash/shell.ts` runs them with brace, tilde, parameter, command, arithmetic, field-splitting and glob expansion, indexed arrays, `local`, `set -euxo pipefail` and the builtins (`cd`, `export`, `read`, `mapfile`, `eval`, `source`, `test`, `printf -v`, `bash -c`, ...), and `src/bash/commands/` holds the commands: file tools, text tools, a `sed` with addresses, ranges, hold space and branches, an `awk` with its own lexer and parser (patterns, ranges, arrays, user functions, `printf`, `getline`, output redirection), a `jq` with generators, path expressions and assignment, and `curl`, which calls the host's `fetch` (no network without one), so a host that passes mppx's paying fetch lets scripts pay MPP services. `BASH_COMMANDS` lists them and `commands` adds or replaces one with a `CommandHandler`. `limits` (`DEFAULT_LIMITS` when the host passes none) bounds commands per call, iterations per loop, call and substitution depth, captured output, pipe and file buffers and wall time; a limit ends the call with a message and exit 126, a timeout or the caller's `signal` with 124. `shell.tool()` gives a host tool (`bashTool()`: `bash` with `{ command }`) and its `call`, whose text is stdout, `[stderr]` and `[exit code N]` cut to 30,000 characters; `new LocalHand({ fetch, bash: shell })` makes `bash` a Code Mode global: a cell calls `await bash("...")` or the tagged template, which quotes interpolated values, and `bash.readFile(path)` and `bash.writeFile(path, text)`, each through the cell host's `bash(script, stdin)`, which runs `exec` with the cell's abort signal, so Dynamic Worker cells reach it over RPC like `fetch`; `BASH_CODE_MODE_INSTRUCTIONS` tells the model, for the session's instructions. `LocalHand` takes any `{ exec(script, { stdin, signal }) }`, so `src/hand.ts` does not import the shell. On 2026-10-22, 388 scripts covering quoting, expansions, control flow, redirections, sed, awk, jq, sort, grep and find gave the same stdout and exit status in this shell as in GNU bash 5.2.21 with GNU coreutils, gawk 5.2.1 and jq 1.7.

`EventHub` keeps a tail of recent contiguous events for readers, wakes waiters and serves a finite or open Server-Sent Events stream from pages the host reads. `new EventHub(retained, retainedBytes)` bounds the tail by both the host's event count and the events' total encoded bytes from `published`, dropping the oldest events first, so a reader behind the tail pages from the log; one event above the byte bound leaves the tail empty. `node --expose-gc scripts/measure-events.mjs` publishes 128 events of 300 B, 4 KiB, 64 KiB and 1 MiB into a hub with the bounds in `EVENT_PAGE_SIZE` and `EVENT_TAIL_BYTES` (128 and 4 MiB by default) and writes the heap each tail retains to `output/events-measurement.json`: on 2026-10-20 in Node 22.23, a count-only tail of 128 1 MiB events retained 134,266,928 bytes, more than an isolate's 128 MB, and 8,437,864 for 64 KiB events, while with the 4 MiB bound the 1 MiB tail kept 3 events in 3,146,448 bytes and the 64 KiB tail 63 in 4,152,544, and the 300 B and 4 KiB tails kept all 128 in 129,288 and 583,032 bytes; parsed event text took about one byte of heap per encoded byte. `Timings` aggregates span durations.

The Rust crate is host glue around the SDK. `src/wasm/bridge.rs` is the ABI and its single-threaded `LocalPool` executor. The module imports `host.dispatch(id, pointer, length)`, `dispatch_body(id, pointer, length, body, body_length)`, `cancel(id)`, `clock(monotonic)` in milliseconds, `random(pointer, length)`, `reply(id, pointer, length)` and `panicked(pointer, length)`, and exports `memory`, `allocate`, `command`, `complete`, `complete_bytes` and `poll`; requests and replies are JSON, and request bodies, model response chunks, socket frames and SQL replies are raw bytes. A `store` or `log` reply is the statements' rows as little-endian `u32` counts of statements, rows and cells, each cell a `u32` byte length (`u32::MAX` for null) followed by its UTF-8 text, so record text crosses without JSON escaping, unescaping or an intermediate `Value`: in `measure-cold.mjs` on 2026-10-20, opening a Claude session with a 2.1 MB checkpoint took a median 14.6 ms instead of 21 ms with its code compiled and 36 ms instead of 42.6 ms in a fresh process, and a Codex session with 3.9 MB of records 25.3 ms instead of 30.5 ms and 59 ms instead of 63 ms. A command is externally tagged, `{"<command>": {fields}}`, so serde reads its fields straight from the request instead of buffering the whole request into its `Content` tree to find an internal `op` tag; on 2026-10-20, built in one directory layout from SDK 139e30458, that removed 82 KB of symbolized `Content` code and shrank the module from 8,345,317 to 8,314,227 bytes (2,530,014 to 2,529,519 gzipped), with `measure-node.mjs` turn times unchanged within run-to-run variation. Each command runs as its own boxed future, so a command compiles only its own code: when one `execute` future inlined every command's future, the first reader command on a restored session made V8 compile 98,633 bytes of function bodies against 59,353 now, and on 2026-10-20 in `measure-cold.mjs` (20-turn sessions with 20 KB replies, 7 rounds, two interleaved runs) that first reader command took a median 3.5 and 3.2 ms instead of 4.3 and 4.1 ms for Claude and 3.3 and 3.3 ms instead of 4.2 and 4.1 ms for Codex, while the function bodies compiled before the first model request fell from 1,325,158 to 1,300,446 bytes for Claude and from 1,475,944 to 1,451,232 for Codex. `src/wasm.rs` is the command table (`configure`, `init`, `submit`, `turn`, `pending`, `cancel`, `interrupted`, `retry`, `finish`, `page`, `import`, `drive`, `attach`, `detach`, `settle`, `preconnect`, `thinking`, `steer`, `dispose`, `catalog`, `admit`): `init` answers a configuration the SDK refuses as a rejection rather than an error, and it builds the runtime with `PLACEMENT_INSTRUCTIONS` when Code Mode has an executor or hands, opens the SDK's `TurnInbox` and maps the commands onto it and onto `SessionLog`. `src/wasm/store.rs` is the SDK's `Sql` host over the `store` and `log` host calls. `src/wasm/transport.rs` implements `nanocode::http::Sender` over `http_start` and `http_read` for both backends, Claude through `SenderTransport` and Codex HTTPS through `host::send_http`, and opens Codex sockets over `socket_open`, `socket_send`, `socket_next`, `socket_wait` and `socket_close`. `src/wasm/events.rs` is the SDK's `InboxHost`: it forwards logged batches over `events`, adds `host_timing`, asks for a finished turn's fields over `turn_finished` and selects each turn's hand with `select_prompt_hand`. `src/wasm/tools.rs` registers host tools as the SDK's `FunctionTool` with a `FunctionHandler` over `tool_call`. `src/wasm/remote.rs` is the `RemoteLink` for the SDK's `RemoteClient` over `remote_catalog`, `remote_send`, `remote_poll` and `remote_close`; it marks batches that hold a request `RemoteFrame::dispatches` reports as starting work, reads catalogs with `RemoteCatalog`, reports as its `max_frame_bytes` the smaller of the host policy and the limit the hand's catalog publishes, and turns a refused or oversized batch into the SDK's unsent error. Protocol, turn and event logic belongs in the SDK.

Install Rust 1.97 or newer, the `wasm32-unknown-unknown` target, and Node.js 22.18 or newer. Run `npm ci`, `cargo check --locked --lib --target wasm32-unknown-unknown`, `npm run check` and `npm run build`. Run SDK checks from `../nanocodex` with `cargo check --locked --lib` and `cargo check --locked --lib --target wasm32-unknown-unknown`. Dependency resolution is pinned by both lockfiles; after moving `sdk-revision.json`, refresh `Cargo.lock` with `cargo metadata --format-version 1` so `--locked` builds pass.

`npm run build` runs `scripts/build.mjs`, then compiles `src/` into `dist/` with `tsconfig.build.json`, which rewrites the `.ts` import extensions to `.js`. The script fingerprints `Cargo.toml`, `Cargo.lock`, every `src` Rust file, the script itself, `../nanocodex/Cargo.toml`, `../nanocodex/Cargo.lock`, every file under `../nanocodex/crates`, toolchain and Cargo configuration files, `rustc --version --verbose` and the `CARGO_` and `RUST` environment, and skips Cargo when the fingerprint and the artifact's digest match `output/wasm-build-fingerprint`. It writes `dist/nanocode_wasm.wasm` only when its bytes change, so a consumer's watcher does not rebuild for unchanged WASM. Local compilation keeps incremental artifacts without debug information. The optimized build uses the `wasm` profile with `opt-level = "s"`: on a 110-turn Worker session with 200 deltas per reply, two runs each measured WASM CPU per turn at 24.0 and 30.5 ms with `"z"` (7.39 MB, 2.31 MB gzipped), 19.1 and 17.8 ms with `"s"` (8.01 MB, 2.48 MB) and 8.4 and 18.7 ms with `3` (10.51 MB, 3.39 MB); `"s"` keeps most of the CPU saving without the larger module every cold start of a hibernated session compiles. `tracing` is built with `max_level_off`: the package installs no subscriber, so every span and event was already disabled at run time, and compiling them out saves 67 KB.

`node scripts/measure-size.mjs` rebuilds the module with symbols into `target/size` and writes its size by crate and its 200 largest functions to `output/wasm-size.json`; it needs `twiggy` (`cargo install twiggy`). Compare sizes built in one directory layout: the checkout's location changes the crates' hashes and with them fat LTO's output, and on 2026-10-19 one Worker commit built in two sibling directories of equal path length measured 8,344,975 and 8,353,723 bytes. Built in each of those two layouts from Worker bc8ac90 and SDK 139e30458, moving the bridge from the Worker into this package and its host-tool adapter into the SDK's `FunctionTool` grew the module by 1,988 and 1,266 bytes, to 8,346,963 and 8,354,989, and by 1,266 and 577 bytes gzipped (`gzip -9`), to 2,530,435 and 2,533,418; at the earlier SDK revision the same move measured 1,971 and 1,987 bytes. The adapter's own code grew by about 300 bytes, since a call now awaits the handler's boxed future inside the tool's, and the rest is LTO output changing with the crate's new name. Moving the turn queue and event log into the SDK's `TurnInbox` and `SessionLog` earlier the same day added 98,798 bytes, 28,234 gzipped, against a build of the same SDK revision without them, and reading every image through `Cursor<&[u8]>` in the SDK removed two extra copies of each image decoder, 247 KB. Nearly all of the module is SDK code that the two providers, subagents and hands use: serde and serde_json code accounts for 1.53 MB of the 7.21 MB of attributed code and functions on serde's buffered `Content` path for tagged and untagged enums for 0.37 MB, image codecs that resize images arriving from hands for 0.45 MB, JSON Schema validation of subagent output contracts (`regress`, `url`, `idna`) for 0.32 MB and arc-swap instantiations for 0.24 MB. Fat LTO already removes the native-only crates of the `nanocode` facade, which contribute 2 KB, and schemars, which contributes nothing. SDK 596d189d2 parses the subagent tools' literal JSON schemas from text instead of expanding `json!` macros, which shrank the module from 8,365,079 to 8,307,405 bytes (2,549,074 to 2,543,220 gzipped) and the function bodies V8 compiles before a restored session's first model request from 1,383,876 to 1,318,292 bytes for Claude and from 1,562,804 to 1,497,194 for Codex. Binaryen's `wasm-opt -Os` would remove another 1.28 MB raw but add 12 KB gzipped, and the npm binaryen package takes about two minutes per build, so the build does not run it.

`node scripts/measure-node.mjs` runs the package in Node with `node:sqlite` as the SQL host and an in-process mock provider: for each backend it opens a session whose model calls the host tool `lookup` once per turn, checks that every request offers the tool and carries no credential, that the tool's result reaches the model and, with `stream_tool_input`, that the logged `tool.input.delta` events of each call concatenate to its arguments, runs two turns, disposes the runtime, reopens the same database in a new instance, checks that the logged events survive and the next request replays the history, and writes timings, model requests, host tool calls and SQL calls to `output/`. On 2026-10-19 on an Apple Silicon laptop, across two runs of both backends, instantiating the compiled module took 0.3 to 0.7 ms, opening a new session 9 to 27 ms, reopening one 6 to 11 ms, a new session's first turn 33 to 50 ms and its second, each with one host tool call, 11 to 16 ms. `NANOCODE_WASM_PATH` selects another compiled module.

`node scripts/measure-cold.mjs [--providers claude,codex] [--rounds 5] [--history 20] [--reply-bytes 20000]` measures the cold path step by step: it builds a session per backend with `--history` turns whose replies carry `--reply-bytes` of text, then in a fresh Node process per round compiles the module, instantiates it, runs a reader command, opens the runtime and runs a turn to its first model request and to completion, runs a warm turn, and repeats instantiation, reader, open and turn on a second instance of the same compiled module, so the difference between the two isolates V8's lazy compilation of the code the cold path runs. It records each store and log transaction the open runs and writes medians and rounds to `output/`. On 2026-10-20 on an Apple Silicon laptop under load from other builds, before the SQL reply and checkpoint reuse changes, a 10-turn Claude session with 20 KB replies took 10 ms to compile, 1.5 ms to instantiate, 4 ms for its first reader command, 28 ms to open and 22 ms more to its first model request, against 0.4, 0.2, 5.5 and 5.7 ms on the second instance; `--no-wasm-lazy-compilation` moved that cost into a 65 ms compile, and V8 compiled 1.38 MB of function bodies before the first Claude request and 1.57 MB before the first Codex one, spread over about 3,300 functions.

`node scripts/benchmark-transfer.mjs 65536 256` compares JSON byte-array round trips with the raw memory copy the bridge uses for HTTP bodies, for 16 MiB of data. It isolates serialization cost, not inference throughput or full application speed; chunk size and count are benchmark inputs.

Keep reports in ignored `output/` and build state in ignored `target/` and `dist/`. Host-specific measurements, such as Durable Object storage rows, workerd CPU and production latency, belong to the consuming host's repository.
