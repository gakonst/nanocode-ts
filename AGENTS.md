# Development

This repository is nanocode-ts (gakonst/nanocode-ts, formerly nanocode-wasm): the nanocode Rust SDK compiled into one WebAssembly module, the TypeScript host that runs it in any JavaScript runtime that can instantiate WebAssembly, such as Cloudflare Workers, Node, Deno and browsers, and TypeScript adapters for Vercel and Cloudflare, so a host repository writes only TypeScript and builds no Rust. Its sibling `../nanocodex` supplies the SDK; `sdk-revision.json` records the SDK master revision this package builds against; check out that revision in the sibling when preparing a fresh workspace. `.github/workflows/release.yml` builds every push to main against the SDK at `sdk-revision.json`, checked out beside it as `nanocodex/`, with the Rust release `rust-toolchain.toml` pins, checks it, packs it and publishes the tarball as the GitHub release `build-<short commit>`. Hosts install that tarball, `"nanocode-ts": "https://github.com/gakonst/nanocode-ts/releases/download/build-<short commit>/nanocode-ts-<short commit>.tgz"`, which their lockfile pins with its integrity: gakonst/nanocode-cloudflare-durable (formerly nanocode-worker) and gakonst/nanocode-vercel-durable; tempoxyz/nanocode-site builds the package from a checkout instead. `dist/` is build output, ignored by Git and listed in `package.json`'s `files`, so the tarball carries the compiled JavaScript, declarations and module and installing it needs neither Rust nor a TypeScript build. Commits before the releases kept `dist/` in Git, so their `github:gakonst/nanocode-ts#<commit>` pins still install. Generic agent, durability, turn and event logic belongs in the SDK, host-agnostic bridge glue in `src/*.ts`, a platform's runtime and wiring in its adapter under `src/<platform>/` (the whole Durable Object runtime in `src/cloudflare/`, the durable-harness app in `src/vercel/`, each with a browser `transport.ts`), so a host repository only configures and skins it, the store and React chat the hosts share in `src/client.ts` and `src/react/`, and an application's own choices (its tools, models, authorization policy, pages and commands) in the host repository.

Do not add code comments, README files, Cargo features, wasm-bindgen glue, tests, or test-only dependencies. The host-agnostic sources use no platform types or bindings: no `DurableObjectState`, no `@cloudflare/workers-types`, no Node APIs; `tsconfig.json` checks `src/*.ts`, `src/cloudflare/sql.ts` and both `transport.ts` files against the standard web platform types only, `tsconfig.vercel.json` checks `src/vercel/*.ts` against Node's, and `tsconfig.cloudflare.json` checks `src/cloudflare/*.ts` against `@cloudflare/workers-types` (the runtime imports `DurableObject` from `cloudflare:workers` and the module as `nanocode-ts/nanocode_wasm.wasm`, which the package resolves to itself); `tsconfig.cloudflare.build.json` emits that directory, which `tsconfig.build.json` leaves out. `package.json` marks only `*.css` as side effects, and every runtime is its own subpath, so a page that imports `nanocode-ts/cloudflare/transport` or `nanocode-ts/vercel/transport` bundles none of the Worker, Node or WebAssembly code. Hosts supply everything platform-specific through the interfaces below or take an adapter's. The Rust side is single-threaded and keeps its state in `thread_local` cells, with no `Mutex` or `RwLock`. TypeScript uses only erasable syntax (`erasableSyntaxOnly`, `verbatimModuleSyntax`) and imports with `.ts` extensions, so Node 22.18 or newer runs the sources directly with type stripping from a checkout or a `file:` link, and bundlers such as esbuild and Wrangler compile them. Limits come from host policy passed in, not from constants here.

`package.json` exports the compiled host as `nanocode-ts`, the adapters as `nanocode-ts/vercel` and `nanocode-ts/cloudflare`, the browser client as `nanocode-ts/client`, the React chat and its Zyzz styles as `nanocode-ts/react`, `nanocode-ts/react/theme` and `nanocode-ts/react/site` with their stylesheet `nanocode-ts/react/zyzz.css`, the code highlighter as `nanocode-ts/highlight`, the model catalog as `nanocode-ts/models`, the simulated shell as `nanocode-ts/bash`, the compiled module as `nanocode-ts/nanocode_wasm.wasm`, with declarations beside each file. `nanocode-ts/models` is generated by `scripts/build.mjs`, which instantiates the module it built and writes `AgentRuntime.modelCatalog()`: each harness's models with their display name, the reasoning efforts the SDK's `ModelCapabilities` allow and its default, whether it takes the priority service tier, the service tiers (`standard`, `fast`, `ultrafast`) and reasoning modes (`standard`, `pro`) its `ModelCapabilities` list as `service_tiers` and `reasoning_modes`, and the gateways that serve it (`direct`, `vercel`, `workers_ai`), so hosts render pickers and validate requests from the SDK instead of copying its tables; a Claude-harness model outside the catalog, such as `zai/glm-5.3`, stays host policy. `nanocode-ts/client` imports nothing, so a page can load `dist/client.js` as a static module: `liveEvent` maps logged events to the vocabulary the Vercel adapter streams (`text`, `reasoning`, `tool_input`, `tool_start`, `tool_end`, `turn`, `retrying`), `Transcript` reveals text and reasoning at 1 − e^(−t/`revealMs`) per frame (instantly with `revealMs: 0` or reduced motion), posts finished paragraphs (`paragraphs`, which keeps code fences whole) as entries, and folds every tool call into one `ToolCell` entry, as the Rust TUI's `bin/nanocode/src/events.rs` does: `tool_input` deltas stream the call's input into it as `ToolInput` decodes it, `tool_start` replaces it with the call's arguments (`describeTool`: a Code Mode `exec` cell's source without its `// @exec:` pragma as `js`, a shell command, a patch or edit as a diff, a file path as the title), nested calls (`parent_call_id`, or a `<parent>/<n>` call id) become its children, `tool.notification` (`tool_output`) shows a running cell's output so far, and `tool_end` (`finishTool`) sets its status, duration, exit code and output with the `Script …`/`Wall time` header stripped; a cell that yields (`Script running with cell ID n`) ends as `yielded`, and the `wait` call on that cell then owns its later nested calls and notifications. A cell is posted once it and every cell started before it finished, and the turn's `turn` event settles any left; until then `live(entries)` receives the running cells and then the paragraph being written. Retry, error, steer and failed-turn events become entries (`describe`) and every other event goes to the host's `apply` in order, `serverEvents` reads a Server-Sent Events body, and `modelItems` and `thinkingItems` build the composer's pickers. `ToolInput` decodes a tool call's input as `tool_input` deltas arrive, in one pass over each delta: `fields` holds each top-level string field of a JSON object, unescaped and growing as the model writes it, and `text()` the only field, `key: value` lines for several, or the raw text of a freeform input such as Codex's `exec` source, so a page can show a file's content or a page's markup while the model writes the call; 600 random chunkings of three inputs (escapes, \u sequences, emoji, a 5 KB field, nested objects and arrays) decoded to the fields `JSON.parse` reads. The three chats, gakonst/nanocode-vercel-durable's, gakonst/nanocode-cloudflare-durable's and nanocode.xyz's, share it. `createConfig({ transport, persist, apply })` in `nanocode-ts/client` is the framework-free store the chats share, as wagmi's `createConfig` is: it runs a `Transcript`, keeps `entries`, `live`, `status` and `error` behind `getState` and `subscribe`, and its `send` notes the prompt and calls the host's `transport.send({ prompt, push, note })`, or `transport.steer` while a turn is pending, settling to idle only after the transcript showed every queued event; `resume` runs `transport.resume` for a turn that kept running while the page was closed. With `history: { key, storage, limit }` the store keeps a conversation history instead of one transcript: `conversations` (id, the first prompt as title, last update) and the open `conversation` in its state, each conversation's entries and its transport's `snapshot()` under `<key>:entries:<id>` and `<key>:transport:<id>` in `localStorage` (or `storage`), the index under `<key>:history`; `select(id)` reopens one with `transport.restore(snapshot)`, `create()` starts one (and `clear()` does too, keeping the old one listed), `remove(id)` forgets one, and none of them act while a turn runs. Both transports implement `snapshot` and `restore` with their session state (session id, event cursor, open turn). `nanocode-ts/react` (`src/react/index.tsx`, React an optional peer dependency) binds it with wagmi-style hooks: `NanocodeProvider({ config, highlight })`, `useConfig`, `useTranscript` (`entries`, `live`), `useSend` (`send`, `isPending`, `isIdle`, `error`), `useNote`, `useHighlighter` and `useConversations` (`conversations`, `current`, `enabled`, `select`, `create`, `remove`), and exports `Chat`, the chat the hosted demos share (the log with `you`/`agent` speakers, the typing line, an `extras` slot, command completion and a host `picker`, the prompt with history on ↑/↓, suggestions and the status line with an `actions` slot and, when the config keeps a history, a `history (n)` button that opens a filterable picker of the conversations with `+ New conversation` first), with `EntryView`, `ToolCell`, `Reply` and `Code` for hosts with their own layout. `ToolCell` renders a cell as the TUI does: a status icon (a spinner and running clock while it runs, then ✓, ✗, ⊘ or ↻), its name, title, duration and details, the input under a │ gutter, nested calls indented under it, and the output, each clipped to a few lines (the input's last lines while it streams) until its header is clicked. `highlight` is a loader, such as `() => import("nanocode-ts/highlight").then(module => module.highlight)`, and `nanocode-ts/highlight` tokenizes with `@pierre/highlights`, an optional peer dependency, in the nanocode light and dark themes. Every style is Zyzz (wevm/zyzz), with no handwritten CSS: `src/react/theme.ts` defines nanocode.xyz's tokens (`tokens`, the commitmono.com palette in light and dark, Commit Mono sizes, spacing in characters) and binds `style`, `variants` and `vars` to them with the config ID `nanocode`; `src/react/styles.ts` holds the chat's definitions, re-exported as `styles` so hosts style their own controls (`styles.row`, `styles.input`, `styles.suggestion({ quiet: true })`) to match; and `src/react/site.tsx` with `site.styles.ts` (`nanocode-ts/react/site`) holds the page chrome the demos share: `styles.body` for `<body>` (base element styles under `:where()`, so component classes win), `Header` with nanocode.xyz's numbered navigation and Experiments menu (gakonst/nanocode-site's `src/Nav.ts`), `Demos`, `Main`, `Page`, `Title`, `Lead`, and `Docs`, `Block`, `Diagram`, `Cards` and `Card` for How It Works pages. Zyzz compiles styles ahead of time and does not compile modules inside `node_modules`, so `scripts/zyzz.mjs`, the last step of `npm run build`, runs `zyzz build dist/react` with the package ID `nanocode-ts` and copies its output over `dist/react`: rewritten modules, a stylesheet per module, `zyzz.css` with all of them, and a `.zyzz.json` contract beside each module, which a host's Zyzz compiler (`zyzz/vite`, `zyzz/next`, `zyzz/esbuild`) reads to compile the host's own `style` calls against the same tokens. Hosts import `nanocode-ts/react/zyzz.css` and declare their own `fontFace`, since the font file is theirs. `src/react/index.tsx` starts with `"use client"` so Next server components can render `site` components; `Code` loads `nanocode-ts/highlight` itself when no `NanocodeProvider` supplies a highlighter. Node's type stripping does not run `.tsx`, so `src/react` is for bundlers only. A bundler that loads `.wasm` imports as `WebAssembly.Module`, as Wrangler does, imports it directly; other hosts compile `dist/nanocode_wasm.wasm` with `WebAssembly.compile`, as the Vercel adapter does.

`nanocode-ts/vercel` runs a session as a durable-harness kernel `Harness` (`nanocodeHarness`, for `durableAgent({ harness })` from `durable-harness`, an optional peer dependency): every SQL write of the SDK's store and turn log is a record-only kernel step `nanocode.sql` keyed `sql:<n>` in the session's Workflow run, each drive replays the committed batches into a `node:sqlite` `:memory:` database (`SqlJournal`, `LocalSql`), submissions become turns of the SDK's `TurnInbox`, host tools are durable-harness `HostTool`s run as kernel steps `tool:<call_id>`, logged events reach the live stream in durable-harness's vocabulary, and model requests go to the Vercel AI Gateway with `AI_GATEWAY_API_KEY` or the Vercel OIDC token (`@vercel/oidc`, an optional peer dependency). A session's provider, model and reasoning effort come from the `nanocode: { provider, model, thinking, max_tokens }` entry of its kernel config when the host starts it with one (`agent.sessions.start({ config })`), as gakonst/nanocode-vercel-durable does for the harness and model a visitor picks, and otherwise from the harness options; the `nanocode.session` effect records them, so every drive opens the same backend and model, and the model endpoint follows the session's provider. A prompt whose whole text is `/effort <level>` is a command, not a turn: the drive checks the level against the session's model with `checkThinking`, records it or the SDK's refusal as that submission's placement, and sends the live stream `{"type":"effort","thinking"}` or an `error`. A submission of kind `steer` that arrives while a turn runs steers it: the drive watches for submissions while `drive` runs (durable-harness's `onHint`, or every `WAIT_POLL_MS` without hints), steers each with its submission ID, records the placement and sends the live stream `{"type":"steered"}`, and `text` and `reasoning` deltas carry the `item` they belong to, the output item or `reasoning:<model call>`, so a reply that follows a steer starts a new message; one that no running turn takes is submitted as a turn when the drive returns. `streamToolInput: true` passes `stream_tool_input`, so the live stream also carries `tool_input` events while the model writes a tool call. `maxPrompts` caps the prompts a session takes, counting every submission but `chaos` and `withdraw` in log order: the drive records a submission past it as placed with `nanocode.refused` and sends the live stream an `error`, and does not steer with it, so a public host enforces its cap inside the drive instead of reading the session before each submission, which cost gakonst/nanocode-vercel-durable 82–108 ms per prompt on 2026-10-21. Every later prompt is submitted with the effort in force as `metadata.thinking`, derived from the placements before it in the run's log so each drive derives the same one, and the drive calls `setThinking` before it drives a turn whose effort differs from the last it applied. `durability: "on"` acknowledges writes at once under the kernel's run-ahead durability and `"strict"` only after their batch commits. `openReader` answers the SDK's reader commands from a session's fold. It reads the module from `dist/nanocode_wasm.wasm` beside itself (`new URL("../nanocode_wasm.wasm", import.meta.url)`). gakonst/nanocode-vercel-durable records its design, limits and measurements.

`nanocode-ts/cloudflare` is the Durable Object side: `DurableObjectSql` is the `SqlHost` over a Durable Object's `storage.sql.exec` and `transactionSync`, with `value_limit` set by its third constructor argument, `SQLITE_VALUE_LIMIT_BYTES` (8 MiB, where workerd's SQLite answers SQLITE_TOOBIG) by default, and an optional observer of each transaction's statements, rows read and written and duration. Cloudflare documents 2 MB per string, BLOB or row for SQLite-backed Durable Objects while workerd stored values of about 8.38 MB in production, so the limit is the host's policy, and a statement that binds a string or BLOB above it throws before any statement of its transaction runs, instead of leaving the failure to SQLite partway through. Its storage type is structural, so the adapter needs no `@cloudflare/workers-types`. gakonst/nanocode-cloudflare-durable builds its session Durable Object on it.

`SqlFileSystem(sql, scope)` from `nanocode-ts/bash` is a `FileSystem` for `Bash` on any `SqlHost`: one `nanocode_files` table (scope, path, parent, kind, data, mtime, mode) written as `store` transactions, so files live wherever the session's SQL does: in the Durable Object's SQLite on Cloudflare and in the journaled SQLite of the Workflow run on Vercel, where they replay with the session. A file is at most the host's `value_limit` (on Cloudflare `createNanocode`'s `valueLimit`, 8 MiB by default); `rename` moves a directory's subtree in one transaction. Both runtimes open a `Bash` on it for every session unless `workspace: false`, at `/workspace` (`workspace.cwd`, seeded with `workspace.files`), and give it to the session twice: as `config.workspace` and the runtime's `workspace` host, so the provider's own workspace tools (Claude's `Bash`/`Read`/`Edit`/`Write`, Codex's `apply_patch`/`exec_command`) run on it, and, with `config.code_mode`, behind the cells' `bash` global, so Code Mode cells call `bash` on the same files; its `curl` uses the cells' `fetch`. The shell's commands follow just-bash's light ones: besides the file and text tools, `tar` (ustar, `-z`), `gzip`/`gunzip`/`zcat` (on `CompressionStream`, file to file, since a command's output is text), `tree`, `rg` (a `grep -rnE` front end), `md5sum`, `od`, `xxd`, `strings`, `split`, `join`, `expand`, `file`, `env`, `which`, `timeout` (it stops waiting, not the command), `yes` (bounded by the output limit) and `ln`, which copies because the filesystem has no links. just-bash's interpreters (`python3`, `sqlite3`, `js-exec`) and its `yq`, `xan` and HTML tools are left out.

`createNanocode(options)` from `nanocode-ts/cloudflare` (`src/cloudflare/runtime.ts`, moved from gakonst/nanocode-cloudflare-durable with `store.ts`, `remote.ts` and `contracts.ts`) returns the `AgentSession` Durable Object class, the Worker `fetch` handler for the sessions API (`sessions/<s>/turns`, `events`, `warm`, `crash`, hands, metrics) and `deleteSession`; its host tools receive the calling agent's `context` in `HostToolCall`, and its egress receives each model request's `provider`; gakonst/nanocode-cloudflare-durable's AGENTS.md documents that API and its options in full. Code Mode is on unless `codeMode: false` (cells run in QuickJS inside the object, with `codeMode.fetch` or no network), a `SqlFileSystem` bash on the object's SQLite is on unless `workspace: false`, tool input streams unless `streamToolInput: false`, and subagents follow the SDK's default, which offers them, unless `subagents: false`. `valueLimit` is the session store's `DurableObjectSql` value limit, `SQLITE_VALUE_LIMIT_BYTES` by default, and its sessions instantiate with it as `log_logical_limit` as well as the store's `value_limit`, so an event above it is still logged as an `omitted` marker, a result above it fails its turn and a prompt above it is `too_large`, while a row whose columns together exceed the physical budget spills its body into `log_parts`; it also bounds a request body: the Worker and the object refuse a larger one with 413. `aiGateway(ai, gateway, serviceTier)` is the egress that sends model requests through a Cloudflare AI Gateway binding, and `PublicLimit` with `client(address)` is a per-visitor rate-limiting Durable Object. `cloudflare({ model, headers, session, url })` from `nanocode-ts/cloudflare/transport` is the browser `Transport` for `createConfig`: it starts and streams turns over the sessions API, reconnects from the last event id, steers a running turn and queues a steer the object refuses with 409 as the next turn, and exposes `warm`, `crash`, `health` and `forget`.

`createNanocode(options)` from `nanocode-ts/vercel` (`src/vercel/app.ts`) builds the durable-harness agent around `nanocodeHarness` with Code Mode, subagents and streamed tool input on by default, and returns `{ agent, GET, POST, chaos }`, so a Next route is `export const { GET, POST } = nanocode`: `POST` starts a session for `{ harness, model, effort, text }` (validated against `options.harnesses` by `selectionOf`), warms one for `{ warm: true }`, and forwards `sessionId` messages and steers to the chat route; `authorize` is a function that throws a `Response` to refuse, or `"public"`. `vercel({ selection, headers, session, url, chaosUrl })` from `nanocode-ts/vercel/transport` is its browser `Transport`.

`AgentRuntime.instantiate(module, sql, { published, wake })` instantiates the module for one session scope; `submit`, `append`, `turn`, `pending`, `page`, `cancel`, `interrupted`, `retry`, `finish`, `import`, `importEvents`, `catalog` and `admit` run on that instance through the SDK's `SessionLog` without opening the SDK session, and `open(config, options)` opens it on the same instance; it cannot be opened twice. `append(scope, events)` logs host-authored events through `SessionLog::append` in one transaction in order with the SDK's own events and publishes them like any logged event: each is `{ request_id?, event }` where `event` is a JSON object with a string `source` naming the host (for example `my-host`), `request_id` attributes it to a turn that is in the log, so `page` with that turn returns it, and the SDK's `source` values `agent` and `subagent` are reserved, so one of them, a missing `source` or an unknown turn refuses the whole batch with nothing logged; an event above `HostOptions.log_logical_limit` is logged as an `omitted` marker like any other and a body above `value_limit` is stored in `log_parts`, and `liveEvent` maps none of them, whatever their `type`, because they are the host's to render, nor does one end a turn's event stream in the Cloudflare runtime or its transport. A host records an annotation such as a runner change in the session's log this way instead of a table of its own, which it would have to merge with the log's order. `config.model` names a model of `config.provider`, such as `gpt-6-luna` or `claude-haiku-5-5`, and `config.thinking` its reasoning effort; without them a session uses Sol or Opus 5.5 at the model's default effort. A Codex session's model must be a Codex model; a Claude session takes any model ID since SDK f96a9a0d7, a Claude model ID or alias or another model a Messages gateway serves, such as `zai/glm-5.3` or `moonshotai/kimi-k3` on the Vercel AI Gateway, and a model the SDK does not know needs `config.max_tokens`, its output limit, which the Rust side applies through `ClaudeHarness::configure`. `config.gateway: "vercel"` routes a Codex API-key session through the SDK's `ResponsesGateway::vercel()`, which names OpenAI models with the gateway's `openai/` prefix and also serves the open-weight GLM-5.3, Kimi K3 and MiMo V2.6 Pro (`config.model` `glm-5.3`, `kimi-k3` or `mimo-v2.6-pro`) as `zai/glm-5.3`, `moonshotai/kimi-k3` and `xiaomi/mimo-v2.6-pro` since SDK 3d983dea2, at `config.endpoint` (`https://ai-gateway.vercel.sh/v1`); a ChatGPT subscription with it is a configuration error, and Claude sessions need only the gateway's Messages URL as `config.endpoint`, since the Vercel AI Gateway accepts Claude's own model IDs. `config.gateway: "workers_ai"` with `config.cloudflare_account_id` runs a Codex API-key session on Workers AI through the SDK's `ChatGateway::workers_ai`, which serves GLM-5.3 (`glm-5.3`) as `@cf/zai-org/glm-5.3` and translates its Responses requests to Chat Completions inside the module: `dispatch` receives them with an `endpoint` ending in `/chat/completions` at that account's `/ai/v1`, and `config.endpoint` is not used. `config.service_tier` (`standard`, `priority`, `fast` or `ultrafast`, the `ServiceTier` type) is a new session's initial service tier, which the SDK sends to OpenAI models as `service_tier: "priority"` and refuses as a configuration error for models without a faster tier, such as Claude models other than Opus 5.5. `config.stream_tool_input: true` logs and publishes the SDK's `tool.input.delta` events, each tool call's input as the model writes it with its `call_id` and `tool`, which `liveEvent` maps to `tool_input` events with `name`, `delta` and `call_id`, so a page can show code, a file or a frame while the model writes the call; it turns on the SDK's `tool_input_deltas` on both backends, and without it the agent emits none, because the log would store every tool input twice. `config.mcp_servers` (`{ name, url, headers?, bearer_token? }`) connects Streamable HTTP MCP servers during `open` through the SDK's `nanocode_mcp_tools` (`src/wasm/mcp.rs`) and registers their tools as the SDK's MCP tools, named, described and converted as natively and offered like host tools; their requests go through `dispatch`, so a paying fetch pays MCP servers too. A server that fails to start fails `open` with a retryable error and an invalid server is a `configuration` refusal; every `open` discovers the servers' tools again. `config.subagents: false` leaves out the delegation tools, `config.providers` opens the other provider's backend as well, so a subagent can select a model of either (the SDK registers every configured backend in one `Harness`, and a child that names a provider the session did not configure fails with "<provider> harness is not configured for this host"): `providers.claude` or `providers.codex` takes that provider's `endpoint`, `subscription`, `gateway`, `cloudflare_account_id` and `max_tokens` as the top-level fields do for the session's own provider, which they keep configuring, so an entry for the session's own provider is a configuration error instead of a second way to set the same thing, and an optional `instructions` that replaces `config.instructions` for that backend's agents, with the hand placement and Code Mode instructions appended to either, so a Claude child gets the host's Claude prompt and a Codex child its own; `stream_tool_input`, `config.tools`, `config.mcp_servers` and the Code Mode host apply to every backend, each backend's agents get their own provider's workspace tools when `config.workspace` is set, and the default model of a backend that is not the session's is Sol. On 2026-10-22 a Claude session that spawned a Codex child dispatched its own requests as `claude` and the child's as `codex`, and the child's Codex requests carried the Codex instructions and the Claude requests only the session's, where without `providers` the same spawn failed with that refusal; with `config.workspace` and an MCP server as well, the root's requests offered `Bash`, `Read`, `Edit` and `Write` and the child's `exec_command`, `write_stdin`, `update_plan` and `apply_patch`, each with the host tool and the MCP tool and neither with the other provider's workspace tools, directly and inside Code Mode, and the MCP requests reached `dispatch` with `provider` null. The `hands` tool is offered only to sessions with a remote executor or hands. On 2026-10-21 through the Vercel AI Gateway, nanocode-vercel-durable's first Luna request with its six workspace tools held 796 input tokens instead of 2,469 (6 KB instead of 17.6 KB, and 2.6 KB instead of 15.5 KB for Claude), and the priority tier moved Luna's median time to first text from 989 to 792 ms over 8 requests each, the slowest from 1,750 to 995 ms. The host passes the configuration through unchanged except for the fields it adds (`runtime_id`, `started_ms` and the defaults of `provider`, `remote`, `hands`, `event_coalesce_ms` and `tools`), and the Rust `Configuration` denies unknown fields, so a misspelled or unsupported field is a `configuration` refusal at `open` instead of a silently ignored one; `scripts/build.mjs` fails when `AgentConfiguration` and the Rust `Configuration` name different fields. Before, `open` copied a fixed list of fields and dropped `max_tokens` until it was added there. `config.instructions` adds host instructions to the agent's developer context, before the hand placement instructions when Code Mode has an executor or hands. `identity` reads the name and runtime ID a hand's catalog advertises, and `catalog` only the name. `retry` records why a turn waits on its host, with an error, kind and next retry time, and `finish` ends a turn the host gives up on as failed or cancelled. `open` throws `HostFailure` with kind `configuration` and `permanent` set when the SDK refuses the runtime configuration or the session it opens, such as a reasoning effort its model does not take, so a host can fail the turn instead of retrying it (before, the session's refusal was a plain error and durable-harness redelivered the drive without end); hosts construct `HostFailure` for their own classifications too. `drive` runs the SDK's `TurnInbox` for one root turn, `settle` reports quiescence, `compact` runs the SDK's `AgentHandle::compact` for a session between turns and answers `{"compacted":true}` once its events are logged and published, or `{"busy":true}` without compacting when a turn is running, a submission is pending in the log, or a subagent or an earlier `compact` is active, because the Claude backend's compaction cancels every running turn, so the check must precede it; a `drive` that arrives while a compaction runs answers `{"waiting":true,"busy":true}` like a second concurrent `drive`, and a `submit` only logs the turn, which the next `drive` runs on the compacted history. Hosts implement these interfaces (`src/contracts.ts`):

- `SqlHost.transaction(kind, operation, statements)` runs one operation's statements in one atomic SQLite transaction and returns each statement's rows as arrays. `SqlHost.value_limit`, when set, is the largest string, BLOB or row the host's SQLite stores: `instantiate` passes it to the module with the `configure` command before any other, and the module gives it to every scope's `SessionLog` as `value_limit`, so owned event bodies and prompts above the physical row budget are stored in immutable content-keyed `log_parts` within that transaction, and `import` batches within the physical binding budget. `HostOptions.log_logical_limit`, when set at `instantiate`, separately bounds logical admission and event sizes: oversized events become `omitted`, results fail the turn and prompts return `{"submitted":"too_large","bytes","limit"}`. Without that option, logical values have no admission cap. `AgentRuntime.page(scope, after, limit, { request_id?, max_bytes? })` bounds decoded event JSON UTF-8 bytes before reading parts; it excludes the crossing event except that it always returns the first event, even with a zero-byte budget. The page envelope is outside the byte budget; bounded pages require a positive event count. Passing a request ID string as the fourth argument keeps the earlier count-only API. - `published(events, bytes)` receives each batch the SDK's `SessionEvents` pump logs, already committed, in sequence order, with each event's encoded JSON size in bytes; `wake()` runs after the SDK's remote Code Mode client receives a batch or finishes a callback, so a host can check quiescence again.
- `dispatch(request, signal, timing)` sends a model or MCP HTTP request with its `method` and returns a fetch `Response`; model requests are `POST`, and an MCP server's event stream is a `GET` whose empty body the host must not forward. `request.provider` is `claude` or `codex` for a model request, the backend that sent it, which in a session with `config.providers` is a child's backend rather than the session's, so a host can route, credential or meter by provider without parsing the endpoint, and null for an MCP request, which no model backend sends. `EventHub` keeps a tail of recent contiguous events for readers, wakes waiters and serves a finite or open Server-Sent Events stream from pages the host reads. `new EventHub(retained, retainedBytes)` bounds the tail by both the host's event count and the events' total encoded bytes from `published`, dropping the oldest events first, so a reader behind the tail pages from the log; one event above the byte bound leaves the tail empty. `node --expose-gc scripts/measure-events.mjs` publishes 128 events of 300 B, 4 KiB, 64 KiB and 1 MiB into a hub with the bounds in `EVENT_PAGE_SIZE` and `EVENT_TAIL_BYTES` (128 and 4 MiB by default) and writes the heap each tail retains to `output/events-measurement.json`: on 2026-10-20 in Node 22.23, a count-only tail of 128 1 MiB events retained 134,266,928 bytes, more than an isolate's 128 MB, and 8,437,864 for 64 KiB events, while with the 4 MiB bound the 1 MiB tail kept 3 events in 3,146,448 bytes and the 64 KiB tail 63 in 4,152,544, and the 300 B and 4 KiB tails kept all 128 in 129,288 and 583,032 bytes; parsed event text took about one byte of heap per encoded byte. `Timings` aggregates span durations.

The Rust crate is host glue around the SDK. `src/wasm/bridge.rs` is the ABI and its single-threaded `LocalPool` executor. The module imports `host.dispatch(id, pointer, length)`, `dispatch_body(id, pointer, length, body, body_length)`, `cancel(id)`, `clock(monotonic)` in milliseconds, `calendar_date(pointer, length)` as the year, month and day of today in an IANA timezone named by UTF-8 text, as one number (year × 10,000 + month × 100 + day) or 0 for an unknown timezone, `random(pointer, length)`, `reply(id, pointer, length)` and `panicked(pointer, length)`, and exports `memory`, `allocate`, `command`, `complete`, `complete_bytes` and `poll`; QuickJS's C is linked against wasi-libc, so the module also imports `wasi_snapshot_preview1`'s `clock_time_get`, `fd_write`, `fd_close`, `fd_fdstat_get` and `fd_seek`, which `AgentRuntime` answers with the host clock and discards output; requests and replies are JSON, and request bodies, model response chunks, socket frames and SQL replies are raw bytes. A `store` or `log` reply is the statements' rows as little-endian `u32` counts of statements, rows and cells, each cell a `u32` byte length (`u32::MAX` for null) followed by its UTF-8 text, so record text crosses without JSON escaping, unescaping or an intermediate `Value`: in `measure-cold.mjs` on 2026-10-20, opening a Claude session with a 2.1 MB checkpoint took a median 14.6 ms instead of 21 ms with its code compiled and 36 ms instead of 42.6 ms in a fresh process, and a Codex session with 3.9 MB of records 25.3 ms instead of 30.5 ms and 59 ms instead of 63 ms. A command is externally tagged, `{"<command>": {fields}}`, so serde reads its fields straight from the request instead of buffering the whole request into its `Content` tree to find an internal `op` tag; on 2026-10-20, built in one directory layout from SDK 139e30458, that removed 82 KB of symbolized `Content` code and shrank the module from 8,345,317 to 8,314,227 bytes (2,530,014 to 2,529,519 gzipped), with `measure-node.mjs` turn times unchanged within run-to-run variation. Each command runs as its own boxed future, so a command compiles only its own code: when one `execute` future inlined every command's future, the first reader command on a restored session made V8 compile 98,633 bytes of function bodies against 59,353 now, and on 2026-10-20 in `measure-cold.mjs` (20-turn sessions with 20 KB replies, 7 rounds, two interleaved runs) that first reader command took a median 3.5 and 3.2 ms instead of 4.3 and 4.1 ms for Claude and 3.3 and 3.3 ms instead of 4.2 and 4.1 ms for Codex, while the function bodies compiled before the first model request fell from 1,325,158 to 1,300,446 bytes for Claude and from 1,475,944 to 1,451,232 for Codex. `src/wasm.rs` is the command table (`configure`, `init`, `submit`, `append`, `turn`, `pending`, `cancel`, and onto `SessionLog`. `src/wasm/store.rs` is the SDK's `Sql` host over the `store` and `log` host calls. `src/wasm/transport.rs` implements `nanocode::http::Sender` over `http_start` and `http_read` for both backends, passing `origin::current()` with `http_start`, `socket_open` and `socket_send`, Claude through `SenderTransport` and Codex HTTPS through `host::send_http`, each over its own Install Rust 1.97 or newer, the `wasm32-unknown-unknown` target, libclang (bindgen generates QuickJS's bindings for this target; set `LIBCLANG_PATH` if it is not found) and Node. `scripts/build.mjs` compiles QuickJS with wasi-sdk: it uses `WASI_SDK_PATH` or downloads wasi-sdk 25 into `target/`, and sets `CC_wasm32_unknown_unknown`, `AR_wasm32_unknown_unknown`, `CFLAGS_wasm32_unknown_unknown`, `BINDGEN_EXTRA_CLANG_ARGS_wasm32_unknown_unknown` and `WASI_SYSROOT` unless set (the C flags force-include the SDK's `crates/runtime/code-mode-engine/wasm/quickjs-wasi.h`, which keeps QuickJS's stack limit on); a bare `cargo check --target wasm32-unknown-unknown` needs the same variables.js 22.18 or newer. Run `npm ci`, `cargo check --locked --lib --target wasm32-unknown-unknown`, `npm run check` and `npm run build`. Run SDK checks from `../nanocodex` with `cargo check --locked --lib` and `cargo check --locked --lib --target wasm32-unknown-unknown`. Dependency resolution is pinned by both lockfiles; after moving `sdk-revision.json`, refresh `Cargo.lock` with `cargo metadata --format-version 1` so `--locked` builds pass.

`npm run build` runs `scripts/build.mjs`, then compiles `src/` into `dist/` with `tsconfig.build.json`, which rewrites the `.ts` import extensions to `.js`. The script fingerprints `Cargo.toml`, `Cargo.lock`, every `src` Rust file, the script itself, `../nanocodex/Cargo.toml`, `../nanocodex/Cargo.lock`, every file under `../nanocodex/crates`, toolchain and Cargo configuration files, `rustc --version --verbose` and the `CARGO_` and `RUST` environment, and skips Cargo when the fingerprint and the artifact's digest match `output/wasm-build-fingerprint`. It writes `dist/nanocode_wasm.wasm` only when its bytes change, so a consumer's watcher does not rebuild for unchanged WASM. Local compilation keeps incremental artifacts without debug information. The optimized build uses the `wasm` profile with `opt-level = "s"`: on a 110-turn Worker session with 200 deltas per reply, two runs each measured WASM CPU per turn at 24.0 and 30.5 ms with `"z"` (7.39 MB, 2.31 MB gzipped), 19.1 and 17.8 ms with `"s"` (8.01 MB, 2.48 MB) and 8.4 and 18.7 ms with `3` (10.51 MB, 3.39 MB); `"s"` keeps most of the CPU saving without the larger module every cold start of a hibernated session compiles. `tracing` is built with `max_level_off`: the package installs no subscriber, so every span and event was already disabled at run time, and compiling them out saves 67 KB.

`node scripts/measure-node.mjs` runs the package in Node with `node:sqlite` as the SQL host and an in-process mock provider: for each backend it opens a session whose model calls the host tool `lookup` once per turn, checks that every request offers the tool and carries no credential, that the tool's result reaches the model and, with `stream_tool_input`, that the logged `tool.input.delta` events of each call concatenate to its arguments, runs two turns, disposes the runtime, reopens the same database in a new instance, checks that the logged events survive and the next request replays the history, and writes timings, model requests, host tool calls and SQL calls to `output/`. On 2026-10-19 on an Apple Silicon laptop, across two runs of both backends, instantiating the compiled module took 0.3 to 0.7 ms, opening a new session 9 to 27 ms, reopening one 6 to 11 ms, a new session's first turn 33 to 50 ms and its second, each with one host tool call, 11 to 16 ms. `NANOCODE_WASM_PATH` selects another compiled module.

`node scripts/measure-cold.mjs [--providers claude,codex] [--rounds 5] [--history 20] [--reply-bytes 20000]` measures the cold path step by step: it builds a session per backend with `--history` turns whose replies carry `--reply-bytes` of text, then in a fresh Node process per round compiles the module, instantiates it, runs a reader command, opens the runtime and runs a turn to its first model request and to completion, runs a warm turn, and repeats instantiation, reader, open and turn on a second instance of the same compiled module, so the difference between the two isolates V8's lazy compilation of the code the cold path runs. It records each store and log transaction the open runs and writes medians and rounds to `output/`. On 2026-10-20 on an Apple Silicon laptop under load from other builds, before the SQL reply and checkpoint reuse changes, a 10-turn Claude session with 20 KB replies took 10 ms to compile, 1.5 ms to instantiate, 4 ms for its first reader command, 28 ms to open and 22 ms more to its first model request, against 0.4, 0.2, 5.5 and 5.7 ms on the second instance; `--no-wasm-lazy-compilation` moved that cost into a 65 ms compile, and V8 compiled 1.38 MB of function bodies before the first Claude request and 1.57 MB before the first Codex one, spread over about 3,300 functions.

`node scripts/benchmark-transfer.mjs 65536 256` compares JSON byte-array round trips with the raw memory copy the bridge uses for HTTP bodies, for 16 MiB of data. It isolates serialization cost, not inference throughput or full application speed; chunk size and count are benchmark inputs.
