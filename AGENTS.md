# Development

nanocode-ts and the hosts built on it (gakonst/nanocode-cloudflare-durable, nanocode-vercel-durable, nanocode-machines-web, tempoxyz/nanocode-site) send models only upstream nanocode's native prompts and tool text: no system or developer instructions of their own, no workspace or sandbox instructions, no tool description overrides (Georgios, 2026-10-25). What models need goes into gakonst/nanocode (its WASM `exec` defaults defer `mcp__*` tools, brief the rarely used subagent tools and note QuickJS, gakonst/nanocode#1085). `instructions` stays an option for other hosts. Mentions below of `LOCAL_INSTRUCTIONS`, `BASH_CODE_MODE_INSTRUCTIONS`, `BASH_REMOTE_PYTHON_INSTRUCTIONS`, the sandbox instructions, `briefTools`, Codex's file-only workspace default and `deferMcp`'s default deferral describe what was removed then: `deferMcp` now defers only with `deferred: true`, and Codex gets all of its native workspace tools. With every host instruction removed, a local GLM-5.3 sweep through the Cloudflare demo Worker passed 12 of 12; the chart prompt needed 17 model calls, since nothing tells models to embed a saved image. Second pass (Georgios, 2026-10-25): nanocode-ts defines no tool text that duplicates or rewrites an upstream tool. `deferMcp` only caches MCP `initialize` and `tools/list` (its `describe_tools`/`call_tool` rewriting, `deferred` and `core` are gone; the SDK defers `mcp__*` tools natively), `Bash` has no `tool()`/`bashTool`/`BASH_TOOL_DESCRIPTION` (no host used them), and the machines cloud tools drop `list_files`, `read_file`, `write_file`, `edit_file` and `delete_file` (upstream Read/Edit/Write and `exec_command` cover the session workspace), leaving `http`, `list_secrets` and `wallet` with one factual line each. On WASM, `AgentRuntime.open` reads the workspace's own `AGENTS.override.md` or `AGENTS.md` through the workspace host and passes it as `environment.project_instructions`, as native nanocode loads a workspace's AGENTS.md (gakonst/nanocode's WASM context source only takes it from the host); tempoxyz/nanocode-site mounts its docs index there. Codex sessions on WASM get every native Codex tool except native-only host routing (`hands`, `runners`): `view_image` reads workspace images through `HostFiles::read_bytes` (the `cell_read` op), and `image_gen__imagegen` posts to `<codex endpoint>/images/generations|edits` through the session's model transport and saves to `generated_images/` through `write_bytes` (`cell_write`), unless the host defines its own `image_gen__imagegen` (gakonst/nanocode#1091). The Cloudflare gateway runs them as the AI Gateway catalog model `openai/<model>` (`gpt-image-2`) and returns OpenAI's `{data: [{b64_json}]}` from the image URL the catalog answers, with edit images as data-URL strings in `images`: AI Gateway added no stored OpenAI key to `openai` provider `images/generations` (401 Missing bearer, while `responses` passed on the same gateway, 2026-10-26). `bench/targets/rust.mjs` reads `nc`'s OpenTelemetry traces from a temporary `--home`, which carry Codex token counts, `code_mode.cell` spans and per-session `agent.depth` for subagents.

`bench/` is the optimization and eval harness, in plain JavaScript with raw-text reports. `node bench/run.mjs --targets=cloudflare,vercel,rust --models=haiku,sol,glm [--probes=a,b] [--conc=1] [--label=x]` runs the probes in `bench/probes.mjs` (cells, bash, file edits, git clone, fetch, parallel calls, python, WebAssembly, notify, yield and wait, store and load, ALL_TOOLS, web search, subagents, charts) against the live Cloudflare demo (`CF_BASE`, `CF_TOKEN`), the Vercel demo (`VERCEL_BASE`) and native Rust (`nc exec` on a machine with Codex and Claude logins; `nc` has no Workers AI route, so no GLM), grades each answer, and writes `bench/out/<label>.jsonl` and a `.txt` table of pass rate, wall time, model calls, first-call and per-turn input tokens, cached share, and wall time split into model, cells, cold runtime start and host overhead, plus a pass grid. `node bench/overhead.mjs` measures Code Mode's own cost in this module in Node with a mock model that answers at once, and `node bench/overhead-native.mjs` the same cells in the SDK's native `code_mode` example (`CODE_MODE_BIN`, a release build). First run, 2026-10-25 (nanocode-ts 08a1208 demos, nc 0.6.7): Cloudflare and Vercel 48 of 48 each, native 32 of 32 (the grader could not see subagents in four native answers, which were correct); host overhead was 9-19% of wall time on Cloudflare, 21-34% on Vercel and 35% on native Haiku, where each run starts a process; an empty cell took 13 ms in Node and 2.2 ms natively, and a million-iteration loop 84 ms and 36 ms in QuickJS. Native logs carry no Codex token counts and no Claude cell spans, and Workers freeze timers between I/O, so those columns read 0 there. The full demo matrix is 13 setups, every model the demos offer: `--targets=cloudflare --models=haiku,sonnet,luna,sol,glm` and `--targets=vercel --models=haiku,sonnet,cglm,ckimi,luna,sol,glm,kimi --conc=2` (`cglm` and `ckimi` are Claude-harness `zai/glm-5.3` and `moonshotai/kimi-k3`, `kimi` Codex `kimi-k3`), 20 probes each with `bigout`, `recursion`, `curl` and the Codex-only `image`; the Cloudflare driver uses nanocode.xyz/cloudflare's public route with a visitor header and both drivers retry 429s. Second run, 2026-10-26 (nanocode-ts 80e7d2d demos): Cloudflare 98 of 98, Vercel 153 of 156, and the three misses (a 524 and a stalled turn on Vercel Claude-harness GLM, a client fetch error) passed on rerun; a full Vercel run costs about $10 of AI Gateway credit.

This repository is nanocode-ts (gakonst/nanocode-ts, formerly nanocode-wasm): the nanocode Rust SDK compiled into one WebAssembly module, the TypeScript host that runs it in any JavaScript runtime that can instantiate WebAssembly, such as Cloudflare Workers, Node, Deno and browsers, and TypeScript adapters for Vercel and Cloudflare, so a host repository writes only TypeScript and builds no Rust. Its sibling `../nanocodex` supplies the SDK; `sdk-revision.json` records the SDK master revision this package builds against; check out that revision in the sibling when preparing a fresh workspace. `.github/workflows/release.yml` builds every push to main against the SDK at `sdk-revision.json`, checked out beside it as `nanocodex/`, with the Rust release `rust-toolchain.toml` pins, checks it, packs it and publishes the tarball as the GitHub release `build-<short commit>`. Before that it publishes the WASM build outputs, `dist/nanocode_wasm.wasm`, `dist/interpreter.wasm`, `dist/models.js` and `dist/models.d.ts` with their digests in `dist/nanocode-wasm.json`, as the asset `nanocode-wasm-<fingerprint>.tgz` of the release `wasm-<fingerprint>` (`node scripts/publish-wasm.mjs --upload`), and checks out the SDK and runs Cargo only when that release does not exist yet. `node scripts/wasm.mjs` prints the fingerprint: the first 20 hex digits of a SHA-256 over `sdk-revision.json`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `scripts/build.mjs`, `scripts/wasm.mjs`, the JavaScript files under `src/wasm`, every `src` Rust file and the interpreter's `Cargo.toml`, `Cargo.lock` and Rust files, so a push that changes only TypeScript reuses the last WASM release. `node scripts/publish-wasm.mjs` without `--upload` writes the asset to `output/`, from `dist/` when its manifest names the current fingerprint, or from a directory or a `build-<commit>` tarball given as its argument, which must come from a commit with the same Rust inputs; only builds against the SDK at `sdk-revision.json` may be uploaded, since the fingerprint does not cover `../nanocodex`. Hosts install the tarball, `"nanocode-ts": "https://github.com/gakonst/nanocode-ts/releases/download/build-<short commit>/nanocode-ts-<short commit>.tgz"`, which their lockfile pins with its integrity: gakonst/nanocode-cloudflare-durable (formerly nanocode-worker) and gakonst/nanocode-vercel-durable; tempoxyz/nanocode-site builds the package from a checkout instead. `dist/` is build output, ignored by Git and listed in `package.json`'s `files`, so the tarball carries the compiled JavaScript, declarations and module and installing it needs neither Rust nor a TypeScript build. To consume a change without waiting for its release, a host pins the commit, `"nanocode-ts": "github:gakonst/nanocode-ts#<commit>"` (`npm install github:gakonst/nanocode-ts#<commit>`, which also updates the lockfile; editing only `package.json` leaves an installed git dependency in place). npm clones the commit, installs its devDependencies and runs `prepare`, `scripts/prepare.mjs`: it keeps `dist/`'s WASM outputs when `dist/nanocode-wasm.json` names the commit's fingerprint and their digests match, else downloads `wasm-<fingerprint>` over HTTPS without authentication (`NANOCODE_TS_WASM_URL` replaces the URL with another URL, a `file:` URL or a path), checks its manifest and copies it into `dist/`, and when no such release exists builds the WASM with `scripts/build.mjs` if Cargo and `../nanocodex` are present, or fails naming the fingerprint. It then runs `npm run build:ts` (both `tsc` builds and `scripts/zyzz.mjs`) unless `output/typescript-build-fingerprint` matches the TypeScript inputs, so npm's second `prepare` while packing the clone is free. Installing a commit that changes only TypeScript takes about 20 seconds; a commit that changes Rust inputs installs once its push to main has published `wasm-<fingerprint>`, and every later TypeScript-only commit at once. `npm install /path/to/nanocode-ts`, its `--install-links` form and `npm pack` run the same `prepare`, as does `npm install` in a checkout. pnpm runs a git dependency's `prepare` only when the host's `pnpm-workspace.yaml` lists it under `allowBuilds` (`nanocode-ts@<resolved spec>: true`). Commits before the releases kept `dist/` in Git, so their `github:gakonst/nanocode-ts#<commit>` pins still install. Generic agent, durability, turn and event logic belongs in the SDK, host-agnostic bridge glue in `src/*.ts`, a platform's runtime and wiring in its adapter under `src/<platform>/` (the whole Durable Object runtime in `src/cloudflare/`, the durable-harness app in `src/vercel/`, each with a browser `transport.ts`), so a host repository only configures and skins it, the store and React chat the hosts share in `src/client.ts` and `src/react/`, and an application's own choices (its tools, models, authorization policy, pages and commands) in the host repository.

Do not add code comments, README files, Cargo features, wasm-bindgen glue, tests, or test-only dependencies. The host-agnostic sources use no platform types or bindings: no `DurableObjectState`, no `@cloudflare/workers-types`, no Node APIs; `tsconfig.json` checks `src/*.ts`, `src/cloudflare/sql.ts` and both `transport.ts` files against the standard web platform types only, `tsconfig.vercel.json` checks `src/vercel/*.ts` against Node's, and `tsconfig.cloudflare.json` checks `src/cloudflare/*.ts` against `@cloudflare/workers-types` (the runtime imports `DurableObject` from `cloudflare:workers` and the module as `nanocode-ts/nanocode_wasm.wasm`, which the package resolves to itself); `tsconfig.cloudflare.build.json` emits that directory, which `tsconfig.build.json` leaves out. `package.json` marks only `*.css` as side effects, and every runtime is its own subpath, so a page that imports `nanocode-ts/cloudflare/transport` or `nanocode-ts/vercel/transport` bundles none of the Worker, Node or WebAssembly code. Hosts supply everything platform-specific through the interfaces below or take an adapter's. The Rust side is single-threaded and keeps its state in `thread_local` cells, with no `Mutex` or `RwLock`. TypeScript uses only erasable syntax (`erasableSyntaxOnly`, `verbatimModuleSyntax`) and imports with `.ts` extensions, so Node 22.18 or newer runs the sources directly with type stripping from a checkout or a `file:` link, and bundlers such as esbuild and Wrangler compile them. Limits come from host policy passed in, not from constants here.

`package.json` exports the compiled host as `nanocode-ts`, the adapters as `nanocode-ts/vercel` and `nanocode-ts/cloudflare`, the browser client as `nanocode-ts/client`, the headless React components as `nanocode-ts/react`, their nanocode skin as `nanocode-ts/react/skin`, its theme and the demos' page chrome as `nanocode-ts/react/theme` and `nanocode-ts/react/site` with their stylesheet `nanocode-ts/react/zyzz.css`, the code highlighter as `nanocode-ts/highlight`, the model catalog as `nanocode-ts/models`, the simulated shell as `nanocode-ts/bash`, machine payments as `nanocode-ts/machines`, `nanocode-ts/machines/local`, `nanocode-ts/machines/server`, `nanocode-ts/machines/react`, `nanocode-ts/machines/cloudflare` and `nanocode-ts/machines/vercel`, the compiled module as `nanocode-ts/nanocode_wasm.wasm`, with declarations beside each file. `nanocode-ts/models` is generated by `scripts/build.mjs`, which instantiates the module it built and writes `AgentRuntime.modelCatalog()`: each harness's models as the SDK's `ModelInfo` lists them from its `ModelCapabilities`, with their display name, the reasoning efforts allowed and the default, whether it takes the priority service tier (`ModelInfo::fast`), the service tiers (`standard`, `fast`, `ultrafast`) and reasoning modes (`standard`, `pro`) its `ModelCapabilities` list as `service_tiers` and `reasoning_modes`, and the gateways that serve it (`direct`, `vercel`, `workers_ai`), so hosts render pickers and validate requests from the SDK instead of copying its tables; a Claude-harness model outside the catalog, such as `zai/glm-5.3`, stays host policy. `nanocode-ts/client` imports nothing, so a page can load `dist/client.js` as a static module: `liveEvent` maps logged events to the vocabulary the Vercel adapter streams (`text`, `reasoning`, `tool_input`, `tool_start`, `tool_end`, `turn`, `retrying`), `Transcript` reveals text and reasoning at 1 − e^(−t/`revealMs`) per frame (instantly with `revealMs: 0` or reduced motion), posts finished paragraphs (`paragraphs`, which keeps code fences whole) as entries, and folds every tool call into one `ToolCell` entry, as the Rust TUI's `bin/nanocode/src/events.rs` does: `tool_input` deltas stream the call's input into it as `ToolInput` decodes it, `tool_start` replaces it with the call's arguments (`describeTool`: a Code Mode `exec` cell's source without its `// @exec:` pragma as `js`, a shell command, a patch or edit as a diff, a file path as the title), nested calls (`parent_call_id`, or a `<parent>/<n>` call id) become its children, `tool.notification` (`tool_output`) appends to a running cell's output (each notification carries only the new output; the cell keeps its last 64 KiB), and `tool_end` (`finishTool`) sets its status, duration, exit code and output with the `Script …`/`Wall time` header stripped (a `duration_ns` of 0 leaves the duration out: a Worker's clock advances only on I/O, so on 2026-10-23 every Code Mode and `run` cell that only computed and called the SQL-backed `bash` over the Cloudflare transport logged 0 and showed `· 0 ms`, with its `tool.call` and `tool.result` at the same `created_at`); a cell that yields (`Script running with cell ID n`) ends as `yielded`, its posted entry marks its still-running nested calls `yielded` too, and the `wait` call on that cell then owns those calls (they move under it and finish there) and its later nested calls and notifications; before 2026-10-24 those calls stayed `running` in the posted cell and showed a spinner after the turn ended. When a turn ends (its `turn` event, or a send or resume that ends without one), the store marks every cell of that turn still `yielded` or `running` in its posted entries, nested calls included, `completed` for a completed turn and `cancelled` otherwise, and forgets the turn's yielded-cell links, so a Stop never leaves a ↻ or spinner behind. Tool output loses its ANSI escape sequences. A cell is posted once it and every cell started before it finished, and the turn's `turn` event settles any left; a later event for a call that was settled that way, or for a new nested call of such a cell that no `wait` owns, is dropped (the last 1,024 settled call IDs are kept), because on 2026-10-24 after Stop on nanocode.xyz/cloudflare/claude the cancelled cell's nested `bash` call ended 20 s later and showed up as a failed row under the next turn's answer; until then `live(entries)` receives the running cells and then the paragraph being written. Retry, error, steer and failed-turn events become entries (`describe`) and every other event goes to the host's `apply` in order. `liveEvent` carries the logged event's `created_at` as `at`, and entries keep `started_at` and `ended_at` (ms) from it, or from the page's clock for events without it: a paragraph or reasoning summary from its stream's first and latest delta, a cell from its start and duration, a note from when it was sent, so a page shows "Thought for 4s" from saved entries. `turns(entries, live, pending)` groups a transcript into turns (`id`, the user `prompt` entry, `blocks` with consecutive paragraphs and consecutive reasoning merged, each with `live`, the turn's `live`, `started_at` and, once it is over, `ended_at`), and `activity(live, pending)` names what a running turn does (`idle`, `waiting`, `thinking`, `writing` or `running` with the `tool`), `serverEvents` reads a Server-Sent Events body, and `modelItems` and `thinkingItems` build the composer's pickers. `ToolInput` decodes a tool call's input as `tool_input` deltas arrive, in one pass over each delta: `fields` holds each top-level string field of a JSON object, unescaped and growing as the model writes it, and `text()` the only field, `key: value` lines for several, or the raw text of a freeform input such as Codex's `exec` source, so a page can show a file's content or a page's markup while the model writes the call; 600 random chunkings of three inputs (escapes, \u sequences, emoji, a 5 KB field, nested objects and arrays) decoded to the fields `JSON.parse` reads. The three chats, gakonst/nanocode-vercel-durable's, gakonst/nanocode-cloudflare-durable's and nanocode.xyz's, share it. `createConfig({ transport, persist, apply })` in `nanocode-ts/client` is the framework-free store the chats share, as wagmi's `createConfig` is: it runs a `Transcript`, keeps `entries`, `live`, `status` and `error` behind `getState` and `subscribe` (`getServerState` is the state a server render without storage produces, which `nanocode-ts/react` hydrates from, so a Next page that renders the chat on the server does not fail hydration with React error 418 when the visitor has a saved conversation), and its `send` notes the prompt and calls the host's `transport.send({ prompt, push, note })`, or `transport.steer` while a turn is pending, settling to idle only after the transcript showed every queued event; a steer's entry (`steer: true`) goes through `Transcript.aside`, which holds it while a paragraph streams and posts it after that paragraph, so a steer does not cut the paragraph in two; `cancel()` calls `transport.cancel` for the running turn, and `cancellable` says whether the transport has one; `resume` runs `transport.resume` for a turn that kept running while the page was closed or the conversation was not open. Each `send` and `resume` is a generation whose parameters carry an `AbortSignal` (`signal`); the store drops the pushes and notes of a generation that is no longer current, and its end no longer touches `status`. With `history: { key, storage, limit }` the store keeps a conversation history instead of one transcript: `conversations` (id, the first prompt as title, last update) and the open `conversation` in its state, each conversation's entries and its transport's `snapshot()` under `<key>:entries:<id>` and `<key>:transport:<id>` in `localStorage` (or `storage`), the index under `<key>:history`, and, while a turn runs, the transcript's running cells, the paragraph being written and its yielded cells (`Transcript.state()`, each text clipped to 64 KiB) under `<key>:live:<id>`. The entries, the live state and the snapshot are written together, in one synchronous step, at most every 250 ms and at once after an entry is posted (a posted entry waits in memory until then; when `localStorage` refuses the live state the store evicts other conversations and, failing that, drops the live state but still saves the cursor), with the snapshot taken when the last processed event arrived, so a reload or a second tab restores the running cells and the paragraph (`Transcript.restore`) and resumes from an event cursor that matches them: before 2026-10-24 the cursor was saved as each event arrived and the live state not at all, so a reload mid-cell lost the running cell, its source and the paragraph being written until the cell ended. Until the same day entries were written as they were posted and the cursor only with the live state, so a refused or skipped live write left the cursor behind the entries and a reload replayed events already shown (once on nanocode.xyz/vercel, a duplicated run row under the final answer). Resume is also idempotent on its own: `Transcript` drops an event whose `seq` it already applied with the same type, call or item and length (the last 4,096 in memory, the last 256 saved with the live state and kept after the turn ends), and the live state keeps the last settled call IDs, so a replay from an old cursor changes nothing, while a takeover drive's new events that reuse a lost `seq` still show. `nanocode-ts/vercel/transport` does not reconnect from a cursor that already carries `;end`. Tabs that share a history coordinate through Web Locks and a `BroadcastChannel` named `nanocode:<key>` (when the page has both): the tab that runs a turn holds the lock `<key>:turn:<conversation>` until its transcript has drained and its last write is saved, and posts its entries, live entries and status for that conversation; another tab showing the conversation follows instead of driving it, shows exactly those entries, writes nothing for it, and forwards its own messages (steers) and Stop to the owner, so steering and cancel stay with one tab. When the lock frees (the turn ended or the owner tab closed), the follower rereads the conversation from storage and calls `resume`, so it continues a turn the closed tab left running. A tab claims the lock before `send` or `resume` and, when another tab changed the conversation's keys since (`storage` events), first rereads its entries, live state and transport snapshot, and it never writes a transport snapshot or live state it did not produce; a tab whose fresh, empty conversation was never saved opens the conversation another tab saves as current. Before 2026-10-25 each tab read storage only at load: on nanocode.xyz/cloudflare/chatgpt and /vercel/chatgpt a second tab showed nothing of a turn sent from the first until reloaded, its own message then started a second turn on the session from its stale cursor, and its next write replaced the first tab's entries, so after a reload that turn was missing from the history. A posted cell keeps at most 64 KiB of input and output, and when `localStorage` refuses a write the store forgets the oldest other conversations until it fits (on 2026-10-24 one 10 MB cell output on the Cloudflare demo stored 1 MB, and every nanocode.xyz demo shares one origin's 5 MB). A send or resume that ends without settling its cells settles them as `cancelled`; `select(id)` reopens one with `transport.restore(snapshot)`, `create()` starts one (and `clear()` does too, keeping the old one listed), `remove(id)` forgets one. While a turn runs they act only when the transport has `resume` (`detachable`): the turn is detached rather than refused, its signal aborts so the transport stops reading and leaves the turn running on the server, the entries it already posted stay in its own conversation (its transcript keeps the paragraph and cells it was showing, in memory, and goes on posting what it had received into that conversation), and `select` then calls `resume`, so reopening the conversation continues the turn from the snapshot's cursor; `remove` of the conversation whose turn runs also calls `cancel`. Without `resume` (an in-tab agent) they still refuse while a turn runs, except `remove` of another conversation. Both transports implement `snapshot` and `restore` with their session state (session id, event cursor, open turn), and honor `signal`: an aborted turn or resume stops its stream and reconnects, keeps the open turn in the snapshot taken when it detached, and never writes to the session state `restore` put in its place. A reconnect that gets 408, 429 or 5xx, or no response, waits `Retry-After` or a delay that doubles from `reconnectMs` up to 15 s and tries again, so a page past the demos' 30 requests a minute goes on following the turn instead of ending it with an error entry. `nanocode-ts/react` (`src/react/index.tsx`, React an optional peer dependency) binds it with wagmi-style hooks: `NanocodeProvider({ config, highlight, skin })`, `useConfig`, `useTranscript` (`entries`, `live`), `useSend` (`send`, `cancel`, `canCancel`, `isPending`, `isIdle`, `error`), `useTurns` (`turns` of the transcript), `useActivity` (`activity`, which `Chat`'s typing line reads), `useNote`, `useHighlighter` and `useConversations` (`conversations`, `current`, `enabled`, `canCreate` and `canSelect`, false while a turn runs unless the config is `detachable`, and `canCreate` also for an empty conversation, `select`, `create`, `remove`), and exports `Chat`, the chat the hosted demos share (the log with `you`/`agent` speakers, the typing line, an `extras` slot, command completion and a host `picker`, the prompt with history on ↑/↓, suggestions (a plain suggestion stays enabled while a turn runs and steers it) and the status line with an `actions` slot, a `stop` button while a cancellable turn runs and, when the config keeps a history, a `history (n)` button that opens a filterable picker of the conversations with `+ New conversation` first), with `EntryView`, `ToolCell`, `Markdown`, `Image` and `Code` for hosts with their own layout. `Markdown` (also exported as `Reply`) renders an assistant entry's markdown with streamdown (vercel/streamdown, a dependency) in its streaming mode: remend closes unfinished bold, italics, links, inline code and fences while text streams, streamdown splits the text into memoized blocks so finished blocks do not re-render, and `Markdown` itself completes a table whose header row or divider is still being written, unless `live` is `false`. Streamdown's own Tailwind-classed components, controls and link-safety modal are replaced: every element is a headless part, `markdown` (its root, `display: contents` in the nanocode skin), `heading` (`level`), `paragraph`, `list` (`ordered`), `item`, `quote`, `table`, `cell` (`header`, `align`), `rule`, `strong`, `em`, `strike`, `inline`, `link` (only `http(s)` and `mailto`), `figure` and `image`, and fenced code goes to `Code` (with `incomplete` while its fence is open) or the host's `code(language, code)`. HTML in the markdown is parsed and sanitized (streamdown's rehype-raw, rehype-sanitize with `data:` image sources allowed, and rehype-harden), and newline-only text between block elements is dropped, because entries keep `white-space: pre-wrap`. `Image` (exported) shows only `http(s)` and `data:image/(png|jpeg|gif|webp|avif|bmp)` URLs (`imageSource`; SVG is left out because a click opens a data image as a same-origin blob), lazily, with its alt text, inside a `figure` link that opens it in a new tab (a data image as a blob URL), falls back to its alt text when it fails to load, and gets `max-width: 100%` inline only when the skin does not style `image`. `finishTool` also collects a tool result's images (`imagesOf`: `input_image` items with `image_url`, `image_url` parts, MCP `image` blocks with `data` and `mimeType`, Anthropic `image` blocks with a base64 or URL `source`, nested in `content`, `content_blocks` or `output`) into the cell's optional `images`, and `ToolCell` shows them under its output as `images`. `ToolCell` renders a cell as the TUI does: a status icon (a spinner and running clock while it runs, then ✓, ✗, ⊘ or ↻), its name, title, duration and details, the input under a │ gutter, nested calls indented under it, and the output, each clipped to a few lines (the input's last lines while it streams) until its header is clicked; with `collapsed` it shows only its header until then. `highlight` is a loader, such as `() => import("nanocode-ts/highlight").then(module => module.highlight)`, and `nanocode-ts/highlight` tokenizes with `@pierre/highlights`, an optional peer dependency, in the nanocode light and dark themes. `NanocodeProvider` calls `highlight` only once a code block with a language other than `text` renders (`useHighlighter(wanted)`), and `Markdown` renders through `React.lazy` from `src/react/markdown.tsx`, which holds every streamdown import: until that chunk loads, which the provider starts on the first idle callback after mount (`preloadMarkdown`), an entry shows its text as one `paragraph` inside `markdown`. - `SqlHost.transaction(kind, operation, statements)` runs one operation's statements in one atomic SQLite transaction and returns each statement's rows as arrays. `SqlHost.value_limit`, when set, is the largest string, BLOB or row the host's SQLite stores: `instantiate` passes it to the module with the `configure` command before any other, and the module gives it to every scope's `SessionLog` as `value_limit`, so owned event bodies and prompts above the physical row budget are stored in immutable content-keyed `log_parts` within that transaction, and `import` batches within the physical binding budget. `HostOptions.log_logical_limit`, when set at `instantiate`, separately bounds logical admission and event sizes: oversized events become `omitted`, results fail the turn and prompts return `{"submitted":"too_large","bytes","limit"}`. - `published(events, bytes)` receives each batch the SDK's `SessionEvents` pump logs, already committed, in sequence order, with each event's encoded JSON size in bytes; `wake()` runs after the SDK's remote Code Mode client receives a batch or finishes a callback, so a host can check quiescence again.
- `dispatch(request, signal, timing)` sends a model or MCP HTTP request with its `method` and returns a fetch `Response`; model requests are `POST`, and an MCP server's event stream is a `GET` whose empty body the host must not forward. `request.provider` is `claude` or `codex` for a model request, the backend that sent it, which in a session with `config.providers` is a child's backend rather than the session's, so a host can route, credential or meter by provider without parsing the endpoint, and null for an MCP request, which no model backend sends. - `remote.execute(request, id)`, `cancel(id)` and `dispose()` carry the SDK's remote Code Mode frames for a configured executor (`connection` null) and for hands. `RemoteExecutor` implements them over any `MessageSocket`: `connect(open, policy)` dials and listens within `timeout_ms`, `accept(socket, policy)` and `restore(socket, policy, catalog)` take a socket whose messages the host forwards to `receive` and `disconnected`, as a hibernating Durable Object does. `connectHand(module, { url, workspace, cwd, fetch, name, WebSocket, transport, onStatus })` (`src/hand.ts`) makes the calling JavaScript host, such as a visitor's browser tab, a hand: it instantiates the module without opening an agent (`AgentRuntime.serveHand`, the commands `hand_open`, `hand_frame` and `hand_closed`), dials the session's `/hands/<name>` WebSocket, publishes the SDK's `Catalog` frame and answers `Request` frames with `src/wasm/hand.rs`, a port of the native hand's frame loop (gakonst/nanocode `tool-runtime/src/remote/native.rs`) onto `LocalCells`: `Execute` and `Wait` run cells in the host with the same prelude (`bash` on the given workspace, `fetch` through `options.fetch`, `wasm` and `WebAssembly` where the shell allows them), progress goes back as `Update` frames, the session's own tools (subagents, host tools) are `Callback` frames answered by `CallbackResult`, and `Cancel`, `CancelTurn`, `DetachTurn`, `BeginTurn`, `Preempt` and `SettlePreempt` map onto the cells' controls. It is not resumable (no `runtime_id`): a reconnect answers `Resume` with `NOT_RECEIVED`, and a closed connection fails pending callbacks. So a durable server session keeps its turn log and receipts while its cells run in the tab, with the tab's native WebAssembly, Pyodide and paying fetch. Every server-side fetch a cell, its bash (`curl`, `wget`, `git clone`) or a paid fetch makes reaches only public http(s) hosts, through `src/egress.ts` (`guard(fetcher, { resolve })`), because cells run on the server and a Vercel Function could otherwise reach its own runtime API at 127.0.0.1 or a cloud metadata service: `publicAddress` refuses loopback, unspecified, private, carrier-grade NAT (100.64/10), link-local (including 169.254.169.254), benchmarking, documentation, multicast and reserved IPv4 and, for IPv6, loopback, IPv4-compatible and IPv4-mapped addresses (checked as their IPv4), NAT64 and 6to4 with a non-public IPv4 inside, Teredo, unique-local (including AWS's fd00:ec2::254), link-local, site-local and multicast; names that end in `localhost`, `.local`, `.localdomain`, `.internal` (`metadata.google.internal`), `.intranet`, `.lan`, `.home.arpa` or the reverse zones, and dotless names (`http://metadata/`), are refused without a lookup; decimal, octal and hex IPv4 forms (`http://2130706433/`, `http://0x7f.1/`, `http://0177.0.0.1/`) arrive normalized by the URL parser and are checked as the address. A hostname is resolved and refused when any of its addresses is not public, and `guard` follows redirects itself (`redirect: "manual"` on every hop, at most 20, with the fetch spec's method and body rewrite, and `authorization`, `cookie` and `proxy-authorization` dropped across origins), checking every hop, so a public URL that redirects to http://127.0.0.1 is refused; a refusal is a 403 with `{"error": "fetch refused: <host> resolves to <address>, which is not a public address"}`. On Node (`src/vercel/egress.ts`, `egress(fetcher?)`) names resolve with `dns.lookup` (all addresses), and without a host fetcher the connection goes through undici's `fetch` with an `Agent` whose `connect.lookup` resolves again and refuses non-public answers, so the address checked is the address connected to and DNS rebinding cannot swap it; `nanocode-ts/vercel`'s harness wraps every cell fetch in it (`sessionFetch`, the static `fetch`, or that pinned fetch when the host passes neither, while bash still gets network only when the host passes a fetch), and `nanocode-ts/machines/vercel`'s accounts pay through it (`src/machines/vercel.ts` is checked with Node's types for this). A host's own static fetch is checked and its redirects followed, but not pinned. Workers have no raw DNS, so the platform-neutral default resolves with DNS over HTTPS (`doh()`, A and AAAA from https://cloudflare-dns.com/dns-query, cached per isolate for the answers' TTL, between 5 s and 300 s) and cannot pin the connection; there Cloudflare's network is the backstop: a Worker's outbound `fetch` cannot reach the machine it runs on or private networks, and Cloudflare documents error 1000 (DNS points to prohibited IP) for a hostname that resolves to a non-public address, which has not been measured on these deployments. `account({ fetch })` sends every paid, MCP, model and locked (`Payment.locked`) request through `guard`; `paying` and the Cloudflare `paying` are marked as already guarded (`mark`, so wrapping them again costs nothing), `nanocode-ts/cloudflare`'s runtime wraps a host's `codeMode.fetch` in `guard`, and `githubArchives` (also marked) follows redirects itself on servers and refuses a hop outside its GitHub allowlist. `publicTarget(url)` is the literal-only check, still exported from `nanocode-ts/machines/server`. `nanocode-ts/sandbox/vercel` and `nanocode-ts/sandbox/cloudflare` (`src/sandbox/`) are `WorkspaceHost`s over real Linux machines, for hosts whose agents outgrow the simulated `Bash` (no processes, interpreter-only WebAssembly on Workers, Pyodide-only Python): a host passes one as the runtime's `workspace` with `/workspace` as `config.workspace`, and its `instructions` replace the simulated shell's in Code Mode. Compare sizes built in one directory layout: the checkout's location changes the crates' hashes and with them fat LTO's output, and on 2026-10-19 one Worker commit built in two sibling directories of equal path length measured 8,344,975 and 8,353,723 bytes. Built in each of those two layouts from Worker bc8ac90 and SDK 139e30458, moving the bridge from the Worker into this package and its host-tool adapter into the SDK's `FunctionTool` grew the module by 1,988 and 1,266 bytes, to 8,346,963 and 8,354,989, and by 1,266 and 577 bytes gzipped (`gzip -9`), to 2,530,435 and 2,533,418; at the earlier SDK revision the same move measured 1,971 and 1,987 bytes. The adapter's own code grew by about 300 bytes, since a call now awaits the handler's boxed future inside the tool's, and the rest is LTO output changing with the crate's new name. Moving the turn queue and event log into the SDK's `TurnInbox` and `SessionLog` earlier the same day added 98,798 bytes, 28,234 gzipped, against a build of the same SDK revision without them, and reading every image through `Cursor<&[u8]>` in the SDK removed two extra copies of each image decoder, 247 KB. Nearly all of the module is SDK code that the two providers, subagents and hands use: serde and serde_json code accounts for 1.53 MB of the 7.21 MB of attributed code and functions on serde's buffered `Content` path for tagged and untagged enums for 0.37 MB, image codecs that resize images arriving from hands for 0.45 MB, JSON Schema validation of subagent output contracts (`regress`, `url`, `idna`) for 0.32 MB and arc-swap instantiations for 0.24 MB. Fat LTO, which the profile used until 2026-10-24, removed the native-only crates of the `nanocode` facade, which contributed 2 KB, and schemars, which contributed nothing. SDK 596d189d2 parses the subagent tools' literal JSON schemas from text instead of expanding `json!` macros, which shrank the module from 8,365,079 to 8,307,405 bytes (2,549,074 to 2,543,220 gzipped) and the function bodies V8 compiles before a restored session's first model request from 1,383,876 to 1,318,292 bytes for Claude and from 1,562,804 to 1,497,194 for Codex. Binaryen's `wasm-opt -Os` would remove another 1.28 MB raw but add 12 KB gzipped, and the npm binaryen package takes about two minutes per build, so the build does not run it.

`node scripts/measure-node.mjs` runs the package in Node with `node:sqlite` as the SQL host and an in-process mock provider: for each backend it opens a session whose model calls the host tool `lookup` once per turn, checks that every request offers the tool and carries no credential, that the tool's result reaches the model and, with `stream_tool_input`, that the logged `tool.input.delta` events of each call concatenate to its arguments, runs two turns, disposes the runtime, reopens the same database in a new instance, checks that the logged events survive and the next request replays the history, and writes timings, model requests, host tool calls and SQL calls to `output/`. On 2026-10-19 on an Apple Silicon laptop, across two runs of both backends, instantiating the compiled module took 0.3 to 0.7 ms, opening a new session 9 to 27 ms, reopening one 6 to 11 ms, a new session's first turn 33 to 50 ms and its second, each with one host tool call, 11 to 16 ms. `NANOCODE_WASM_PATH` selects another compiled module.

`node scripts/measure-cold.mjs [--providers claude,codex] [--rounds 5] [--history 20] [--reply-bytes 20000]` measures the cold path step by step: it builds a session per backend with `--history` turns whose replies carry `--reply-bytes` of text, then in a fresh Node process per round compiles the module, instantiates it, runs a reader command, opens the runtime and runs a turn to its first model request and to completion, runs a warm turn, and repeats instantiation, reader, open and turn on a second instance of the same compiled module, so the difference between the two isolates V8's lazy compilation of the code the cold path runs. It records each store and log transaction the open runs and writes medians and rounds to `output/`. On 2026-10-20 on an Apple Silicon laptop under load from other builds, before the SQL reply and checkpoint reuse changes, a 10-turn Claude session with 20 KB replies took 10 ms to compile, 1.5 ms to instantiate, 4 ms for its first reader command, 28 ms to open and 22 ms more to its first model request, against 0.4, 0.2, 5.5 and 5.7 ms on the second instance; `--no-wasm-lazy-compilation` moved that cost into a 65 ms compile, and V8 compiled 1.38 MB of function bodies before the first Claude request and 1.57 MB before the first Codex one, spread over about 3,300 functions.

`node scripts/benchmark-transfer.mjs 65536 256` compares JSON byte-array round trips with the raw memory copy the bridge uses for HTTP bodies, for 16 MiB of data. It isolates serialization cost, not inference throughput or full application speed; chunk size and count are benchmark inputs.
